# Lessons Learned

## Role
이 문서는 이번 프로젝트에서 실제로 놓쳤던 문제를 기록하고, 다음 프로젝트에서는 같은 문제를 다시 만들지 않기 위한 기본 규칙을 남긴다.

## Scope
- 남기는 것:
  - 문서-구현 불일치
  - 배포/env 누락
  - 외부 source hang
  - 데이터 품질 오판정
  - 완료 판정 기준이 흐렸던 것
- 남기지 않는 것:
  - 단순 구현 디테일
  - 일회성 코드 버그
  - 다시 쓰지 않을 세부 상황

## 1. 문서-구현 불일치를 너무 늦게 발견했다

### 실제로 놓친 것
- 문서에는 Google 로그인, 도메인 제한, `401/403` 계약이 있었지만 실제 구현은 빠져 있었다.
- 일부 화면/책임 분리 규칙은 문서에 있었지만 코드에는 완전히 반영되지 않은 상태로 진행됐다.

### 왜 못 잡았나
- 구현과 blocker 해소에 집중하면서, `문서 기준 필수 사용자 흐름`을 별도 게이트로 두지 않았다.
- 기능 단위 구현 검증은 했지만, `문서 ↔ 구현 ↔ 배포`를 한 번에 대조하는 검사는 늦게 했다.

### 다음 기본 규칙
- 구현 시작 전에 `문서 기준 필수 흐름`을 목록화하고, 완료 판정 전 반드시 다시 대조한다.
- 특히 인증, 권한, 주요 엔드포인트, 화면 책임 분리는 P0 항목으로 따로 점검한다.
- 문서에 있는 규칙이 코드에 없으면 “나중에 붙이자”가 아니라 즉시 gap으로 기록한다.

## 2. 배포/env 문제를 너무 늦게 확인했다

### 실제로 놓친 것
- Railway 배포는 떠 있었지만 `DATABASE_URL` 누락으로 API가 실패했고, 화면은 셸만 보이는 상태였다.
- 로컬 성공과 배포 성공을 같은 것으로 취급했다.

### 왜 못 잡았나
- 배포 후 `헬스 체크 엔드포인트`를 필수 단계로 두지 않았다.
- 앱이 200 HTML을 반환하면 서비스가 정상이라고 과신했다.

### 다음 기본 규칙
- 배포 직후 최소 3개를 반드시 확인한다.
  - 메인 URL 응답
  - 헬스 체크 API 응답
  - DB 연결이 필요한 실제 데이터 API 응답
- `앱이 뜬다`와 `데이터가 나온다`를 분리해서 본다.
- 필수 env는 서비스별로 체크리스트로 관리하고, 배포 후 실제 런타임에서 다시 확인한다.

## 3. 외부 source hang을 너무 늦게 runtime 관점으로 봤다

### 실제로 놓친 것
- Slack, Gmail, Salesmap 경로가 refresh 전체를 오래 붙잡거나 `running` 상태로 남았다.
- 한 source의 느린 응답이 전체 orchestration을 계속 점유했다.

### 왜 못 잡았나
- source별 timeout, source budget, concurrency 제한을 처음부터 기본값으로 넣지 않았다.
- collector가 끝나는지보다 “결국 끝나겠지”라는 가정으로 route를 먼저 붙였다.

### 다음 기본 규칙
- 외부 source collector에는 기본적으로 아래 3개를 넣는다.
  - request timeout
  - source 또는 scope 단위 budget
  - concurrency 제한
- `route 성공` 전에 `collector 단독 benchmark`와 `source 단위 종료 보장`을 먼저 확인한다.
- `running` 상태가 남는 파이프라인은 실패 정리 방법까지 함께 설계한다.

## 4. 데이터 품질 문제를 기능 완료와 분리해서 보지 못했다

### 실제로 놓친 것
- 특수 금액 판정처럼 파이프라인은 성공하지만 데이터는 잘못 분류되는 케이스가 뒤늦게 드러났다.
- “응답이 나온다”와 “데이터가 맞다”를 한동안 같은 것으로 취급했다.

### 왜 못 잡았나
- 구현 성공과 데이터 정확도 검증을 별도 트랙으로 운영하지 않았다.
- source별 대표 edge case를 먼저 문서화하지 않고 코드부터 붙였다.

### 다음 기본 규칙
- 데이터 품질은 최소 3종류로 따로 검증한다.
  - 정상 케이스
  - 경계 케이스
  - 오분류 가능성이 높은 반례
- 기능 완료 보고에 `데이터 정확도 미검증` 상태를 명확히 분리해서 적는다.
- 정책 문구가 애매하면 코드 해석으로 덮지 말고, 먼저 정책 문서에 적용 범위를 명확히 적는다.

## 5. 완료 판정 기준이 흐려서 “성공”의 의미가 섞였다

### 실제로 놓친 것
- `build PASS`, `API 응답`, `데이터 정확도`, `배포 성공`, `full refresh E2E`가 한동안 같은 “완료”로 섞여 있었다.
- 결과적으로 “기술적으로는 성공”과 “운영 준비 완료”를 같은 표현으로 쓰기 쉬웠다.

### 왜 못 잡았나
- 완료 판정을 한 층으로만 봤고, 단계별 성공 정의를 분리하지 않았다.
- `구현 성공`, `runtime 성공`, `데이터 품질 통과`를 별도 라벨로 관리하지 않았다.

### 다음 기본 규칙
- 완료 판정은 최소 아래 4단계로 분리한다.
  - 구현 성공
  - 배포 성공
  - route/runtime 성공
  - 데이터 품질 통과
- 보고 문구에는 항상 현재 달성한 단계와 아직 남은 단계를 함께 적는다.
- “MVP 완료” 표현은 최소한 헬스 체크와 핵심 사용자 흐름 검증이 끝난 뒤에만 사용한다.

## 6. source `success`와 실제 데이터 반영 성공을 같은 뜻으로 썼다

### 실제로 놓친 것
- Gmail/Slack source가 예외 없이 끝나면 `success`로 기록됐고, 실제 instructor aggregate 반영이 0건이어도 겉으로는 정상처럼 보였다.
- 결과적으로 “메일을 한 건도 못 끌어왔는데 왜 success냐” 같은 해석 충돌이 발생했다.

### 왜 못 잡았나
- source 상태를 “기술적으로 끝났는가” 기준으로만 정의했고, “canonical 반영이 있었는가”를 별도 상태로 다루지 않았다.
- `source_sync_logs`와 `GET /api/status`에 raw 수집 건수와 반영 건수를 같이 노출하지 않았다.

### 다음 기본 규칙
- 외부 source status는 최소 아래 3가지를 구분한다.
  - 호출/수집 성공
  - canonical 반영 성공
  - 데이터 품질 경고가 있는 부분 성공(`partial`)
- `success`는 “에러가 없었다”가 아니라 “기술적 성공 + partial 조건 없음”으로 정의한다.
- 상태 API에는 source별 `fetched_count`, `updated_count`, `note`를 같이 노출해 운영자가 즉시 해석할 수 있게 한다.
