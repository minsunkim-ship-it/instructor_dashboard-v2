# 강사 DB 대시보드 구현 명세서 v2

## 1. 목적

데이원 B2B 구성원이 강사 정보를 한 화면에서 탐색하고 조회할 수 있는 내부 운영 대시보드를 구현한다.

## 2. 구현 범위

### 2-1. 이번 버전 포함

- 강사 목록 조회
- 검색, 필터, 정렬
- 강사 상세 조회
- 강사 프로필 요약 표시
- 핵심 수치 표시
- 점수 구성 요소 표시
- 만족도 표시
- 운영 인텔리전스 표시
- 강의 이력 표시
- 단가 이력 표시
- 운영 메모 표시
- 데이터 상태 표시
- 수동 새로고침
- API 실패 시 fallback 처리
- 마스터 데이터셋 기반 조회
- 계약시트, 노션, 세일즈맵, 지메일, 슬랙 기반 데이터 조회

### 2-2. 이번 버전 제외

- 강사 비교 전용 화면
- 편집 기능
- JSON import/export (아예 삭제)
- 권한 분리
- 자동 배정
- 계약/정산/메시지 발송
- 모바일 앱
- 고도화된 운영 인텔리전스 자동 생성

## 3. 공통 규칙

- 본 버전은 `read-only` 조회 서비스로 구현한다.
- 로그인은 Google 로그인을 사용한다.
- 기본 접근 허용 대상은 `@day1company.co.kr` 도메인 계정으로 제한한다.
- `@day1company.co.kr` 계정이 아닌 경우 로그인 또는 접근을 허용하지 않는다.
- 본 버전에서는 로그인한 사용자 모두 동일한 정보를 조회할 수 있다고 가정한다.
- 연락처와 운영 메모는 내부 사용자 기준으로 원문을 그대로 노출한다.
- 기본 레이아웃은 `목록 + 상세 패널` 구조를 사용한다.
- 첫 진입 시 상세 패널은 빈 상태로 두고, 사용자가 강사를 선택한 뒤에만 상세 정보를 표시한다.
- 값이 없는 필드는 `-`로 표시한다.
- 배열 값이 비어 있으면 해당 영역은 숨기거나 빈 상태 문구를 표시한다.
- 날짜는 `YYYY.MM.DD` 또는 서비스 표준 포맷으로 통일한다.
- 금액은 `원` 기준 숫자를 받아 화면에서는 `만원/시간` 또는 지정 포맷으로 변환한다.
- API 실패 시 fallback 데이터로 화면을 유지한다.
- fallback 상태에서는 상단에 `임시 데이터 표시 중` 배너를 노출한다.
- 추측 매칭은 허용하지 않는다.
- 병합/검증 실패 데이터는 원본과 구분 가능해야 한다.

## 4. 상태 정의

- `idle`: 초기 상태
- `loading`: 목록 또는 상세 데이터 로딩 중
- `success`: 정상 렌더링
- `empty`: 결과 없음
- `partial`: 일부 필드 누락
- `error`: API/처리 실패
- `fallback`: fallback 데이터 사용 중

### 5-3. 타입 정의

#### ScoreBreakdown

Engagement Score를 구성하는 7개 컴포넌트의 개별 점수를 담는다.

```
ScoreBreakdown {
  courses: number          // 출강횟수 (0~35)
  satisfaction: number     // 만족도 (0~15)
  slack: number            // 슬랙 활동 (0~15)
  recency: number          // 최근성 (0~15)
  salesmap: number         // 세일즈맵 딜 (0~10)
  email: number            // 이메일 활동 (0~5)
  ops_channel: number      // 운영 채널 활동 (0~5)
}
```

#### Satisfaction

강사의 만족도 정보를 담는다.

```
Satisfaction {
  avg_score: number | null   // 만족도 평균 (1.0~5.0)
  response_count: number     // 응답 수
  is_imputed: boolean        // 중앙값 대체 여부 (true이면 실제 수집값이 아닌 대체값)
}
```

#### FeeHistory

단가 변동 이력 1건을 담는다.

```
FeeHistory {
  date: string               // 변경 날짜 (YYYY-MM-DD)
  amount: number             // 금액 (원 단위)
  context: string | null     // 변경 사유
  source: string | null      // 출처 (노션/세일즈맵/계약시트 등)
}
```

#### TeachingHistory

강의 이력 1건을 담는다.

```
TeachingHistory {
  company: string            // 기업명
  course: string             // 과정명
  dates: string              // 일정 (YYYY-MM-DD)
  deal_fee_hourly: number | null // 해당 출강 건의 시간당 단가 (원 단위)
  note: string | null        // 특이사항
}
```

### 5-4. 상세 조회 성공 조건

- `base_fee_hourly`

위 필드 중 1개 이상 누락 시 `partial` 상태로 판정한다.

## 7. 기능별 명세

### Feature A. 강사 목록 조회

### 목적

사용자가 대시보드에 들어오자마자 강사 후보를 빠르게 훑어보고, 한 명을 선택해 상세 정보를 확인할 수 있어야 한다.

### 화면 구조

- 화면은 2단 구조로 만든다.
- 왼쪽은 강사 목록 영역, 오른쪽은 강사 상세 영역으로 구성한다.
- 왼쪽 목록 영역 너비는 고정형으로 두고, 오른쪽 상세 영역이 나머지 공간을 사용한다.
- 이 기능은 데스크톱 기준으로 설계한다.

### 목록 영역 구성

- 목록 영역 상단에는 아래 요소를 배치한다.
  - 대시보드 제목
  - 전체 강사 수
  - 마지막 업데이트 시각
  - 검색창
  - 카테고리 필터
  - 정렬 선택

### 목록 아이템 구성

강사 1명은 목록에서 1개의 카드형 행으로 보여준다.

각 행은 아래 구조를 따른다.

- 가장 왼쪽: 순위 배지
- 가운데: 강사 기본 정보
- 가장 오른쪽: 핵심 수치 요약

### 강사 기본 정보 영역

강사 기본 정보 영역에는 아래 순서로 표시한다.

- 첫 줄: 강사명
- 강사명 오른쪽: 운영상 주의가 있으면 배지 표시
- 둘째 줄: 카테고리 · 소속
- 셋째 줄: 전문분야 최대 2개

### 핵심 수치 요약 영역

오른쪽에는 아래 정보만 표시한다.

- 점수
- 총 출강 횟수
- 기본 단가

단, 순위와 점수가 모두 있는 경우:

- 순위는 왼쪽 배지로 표시
- 점수는 오른쪽 숫자로 표시

### 노출 규칙

- 강사명은 목록에서 가장 눈에 띄게 보여야 한다.
- 카테고리와 소속은 보조 정보로 보여야 한다.
- 전문분야는 최대 2개까지만 보여준다.
- 전문분야가 3개 이상이어도 목록에서는 더 보여주지 않는다.
- 총 출강 횟수는 `N회` 형식으로 표시한다.
- 기본 단가는 `N만원/시간` 형식으로 표시한다.
- 전임강사인 경우 강사명 옆 또는 보조 정보 영역에 `전임강사` 배지를 함께 표시한다.
- 점수는 소수점 없이 정수로 표시한다.
- 점수가 없으면 점수 영역은 숨기고, 순위만 표시한다.
- 카테고리나 소속이 없으면 `-`로 표시한다.
- 전문분야가 없으면 셋째 줄은 숨긴다.

### 아이템 크기와 밀도

- 목록 아이템은 한 화면에서 여러 명을 빠르게 훑어볼 수 있도록 촘촘한 밀도를 유지한다.
- 각 아이템은 3줄 구조로 고정한다.
- 너무 긴 텍스트는 줄바꿈하지 않고 말줄임 처리한다.
- 한 행 높이는 일정하게 유지한다.

### 선택 상태

- 사용자가 강사를 클릭하면 해당 행은 선택 상태로 바뀌어야 한다.
- 선택된 항목은 배경색 또는 테두리로 다른 항목과 분명히 구분한다.
- 한 번에 1명만 선택 가능하다.

### 기본 정렬

- 목록 기본 정렬은 점수 높은 순으로 한다.
- 점수가 없는 경우 순위가 높은 순으로 정렬한다.
- 점수와 순위가 모두 없으면 이름순으로 정렬한다.

### 로딩 상태

- 데이터를 불러오는 중에는 목록 전체 대신 로딩 상태를 보여준다.
- 로딩 상태에서는 `강사 데이터를 불러오는 중입니다` 문구를 표시한다.

### 빈 상태

- 목록 데이터가 없으면 `등록된 강사가 없습니다` 문구를 표시한다.
- 검색 결과가 없으면 `검색 결과가 없습니다` 문구를 표시한다.

### 오류 및 fallback 상태

- API 호출에 실패했지만 대체 데이터가 있으면 목록은 계속 보여준다.
- 이 경우 목록 상단에 `임시 데이터 표시 중` 안내를 표시한다.
- 일부 강사의 값이 비어 있어도 목록 전체는 정상적으로 보여야 한다.
- 이름이나 식별 정보가 없는 항목은 목록에서 제외한다.

### 클릭 동작

- 사용자가 목록에서 강사를 클릭하면 페이지 이동 없이 오른쪽 상세 영역이 열려야 한다.
- 상세 영역이 이미 열려 있는 경우 선택된 강사 정보만 바뀐다.

### 이번 버전에서 확정한 디자인 판단

- 목록은 카드형 리스트로 한다.
- 순위는 왼쪽 원형 배지로 표시한다.
- 운영상 주의 정보는 강사명 옆 배지로 표시한다.
- 전문분야는 2개까지만 노출한다.
- 점수와 출강 횟수, 단가는 오른쪽 요약 영역에 세로로 정리한다.
- 긴 텍스트는 말줄임 처리한다.
- 한 행은 3줄 구조로 고정한다.
- 데스크톱 기준 좌측 목록, 우측 상세 패널 구조로 간다.

### 구현 완료 기준

- 강사 목록이 기본 정렬 규칙에 따라 노출된다.
- 각 행에 이름, 카테고리, 소속, 전문분야, 출강 횟수, 단가, 순위 또는 점수가 보인다.
- 사용자가 한 명을 선택할 수 있다.
- 선택 상태가 눈에 띄게 구분된다.
- 로딩, 빈 상태, fallback 상태가 각각 구분되어 보인다.
- 일부 데이터가 비어 있어도 화면이 깨지지 않는다.

### Feature B. 검색

### 목적

사용자가 원하는 강사를 텍스트로 빠르게 찾을 수 있어야 한다.
검색은 강사 목록을 좁히는 가장 기본적인 탐색 수단으로 동작해야 한다.

### 화면 위치

- 검색창은 강사 목록 영역 상단에 배치한다.
- 검색창은 대시보드 제목 및 메타 정보 아래, 카테고리 필터와 정렬 선택 위에 배치한다.
- 사용자가 목록을 탐색하는 동안 항상 쉽게 찾을 수 있어야 한다.

### 검색창 구성

- 검색 기능은 하나의 단일 입력창으로 제공한다.
- 입력창 왼쪽에는 검색 아이콘을 배치한다.
- 입력창에는 placeholder 문구를 표시한다.

placeholder 문구:

- `강사 이름, 전문분야 검색...`

### 검색 대상

검색은 아래 항목을 대상으로 동작해야 한다.

- 강사명
- 카테고리
- 전문분야
- 소속

### 동작 방식

- 사용자가 검색창에 텍스트를 입력하면 목록 결과가 즉시 갱신되어야 한다.
- 검색은 입력과 동시에 적용되는 방식으로 동작한다.
- 별도의 검색 버튼은 두지 않는다.
- 검색어가 비어 있으면 전체 목록을 다시 보여줘야 한다.

### 검색 규칙

- 검색어 앞뒤 공백은 제거한다.
- 대소문자는 구분하지 않는다.
- 부분 일치 검색을 지원한다.
- 초성 검색은 지원하지 않는다.
- 형태소 분석 기반 검색은 지원하지 않는다.
- 오타 교정 검색은 지원하지 않는다.

### 검색 결과 표시 규칙

- 검색 결과는 기존 목록 영역 안에서 그대로 갱신한다.
- 검색 결과 개수에 따라 현재 표시 중인 목록 수가 반영되어야 한다.
- 검색 결과가 많아도 목록 구조 자체는 바뀌지 않아야 한다.

### 검색어 유지 규칙

- 사용자가 입력한 검색어는 입력창에 그대로 유지되어야 한다.
- 사용자가 강사를 클릭해 상세 화면을 열어도 검색어는 유지된다.
- 새로고침이 일어나더라도 현재 검색어는 유지한다.

### 필터 및 정렬과의 관계

- 검색은 카테고리 필터와 동시에 적용될 수 있어야 한다.
- 검색 결과에는 현재 선택된 정렬 기준이 그대로 적용되어야 한다.
- 즉, 검색은 목록을 좁히는 역할을 하고, 정렬은 그 결과의 순서를 정하는 역할을 한다.

### 빈 상태

- 검색 결과가 0건이면 목록 영역에 `검색 결과가 없습니다` 문구를 표시한다.
- 이 경우 기존 강사 목록 대신 빈 결과 상태를 보여준다.

### 예외 상황

- 일부 강사 데이터에서 카테고리, 전문분야, 소속 값이 비어 있어도 검색 기능 전체는 정상 동작해야 한다.
- 이름이나 식별 정보가 없는 잘못된 데이터는 검색 대상에서 제외한다.
- fallback 데이터 사용 중에도 검색은 동일하게 동작해야 한다.

### 이번 버전에서 확정한 디자인 판단

- 검색창은 목록 상단의 전체 너비를 사용하는 단일 입력창으로 만든다.
- 입력창 왼쪽에는 검색 아이콘을 둔다.
- 검색 버튼은 두지 않는다.
- 검색어 입력 즉시 결과가 반영되는 구조로 간다.
- 검색 결과가 없을 때는 목록 영역 중앙에 빈 상태 메시지를 보여준다.
- 입력창 높이는 목록 상단 UI와 어울리는 컴팩트한 형태로 유지한다.

### 구현 완료 기준

- 사용자가 검색창에 텍스트를 입력하면 목록이 즉시 좁혀진다.
- 강사명으로 검색할 수 있다.
- 카테고리로 검색할 수 있다.
- 전문분야 키워드로 검색할 수 있다.
- 소속으로 검색할 수 있다.
- 검색어가 비어 있으면 전체 목록이 다시 보인다.
- 검색 결과가 없으면 빈 상태 문구가 보인다.
- 필터와 정렬을 함께 써도 검색이 정상 동작한다.

### Feature C. 필터

### 목적

사용자가 카테고리 기준으로 강사 목록을 빠르게 좁혀볼 수 있어야 한다.
필터는 검색과 함께 목록 탐색을 돕는 기본 기능으로 동작해야 한다.

### 화면 위치

- 카테고리 필터는 강사 목록 영역 상단에 배치한다.
- 검색창 아래, 정렬 선택과 같은 상단 제어 영역 안에 배치한다.
- 사용자가 현재 어떤 카테고리를 보고 있는지 쉽게 알 수 있어야 한다.

### 필터 구성

- 필터는 카테고리 목록을 선택할 수 있는 형태로 제공한다.
- 이번 버전에서는 단일 선택 필터로 시작한다.
- 기본값은 `전체`다.

표시 항목 예시:

- 전체
- 생성형AI
- 데이터사이언스
- 업무생산성
- 기타 카테고리

### 동작 방식

- 사용자가 특정 카테고리를 선택하면 해당 조건에 맞는 강사만 목록에 표시되어야 한다.
- 필터는 검색과 동시에 적용될 수 있어야 한다.
- 필터 변경 시 목록 결과는 즉시 갱신되어야 한다.
- `전체`를 선택하면 전체 강사 목록으로 다시 돌아가야 한다.

### 필터 규칙

- 한 번에 하나의 카테고리만 선택할 수 있다.
- 현재 선택된 카테고리는 시각적으로 구분되어야 한다.
- 카테고리 값이 없는 강사는 `전체`에서는 보일 수 있지만, 특정 카테고리 필터에는 포함되지 않는다.
- 필터는 현재 선택된 정렬 기준을 유지한 상태로 적용된다.

### 검색 및 정렬과의 관계

- 검색어가 있는 상태에서도 필터는 정상적으로 적용되어야 한다.
- 필터 적용 후에도 정렬 기준은 유지되어야 한다.
- 즉, 검색과 필터는 목록을 좁히고, 정렬은 그 결과의 순서를 정한다.

### 상세 선택 상태 처리

- 필터 변경 후 현재 선택된 강사가 결과에 남아 있으면 선택 상태를 유지한다.
- 현재 선택된 강사가 필터 결과에 포함되지 않으면 선택 상태를 해제하고 상세 영역을 빈 상태로 전환한다.

### 빈 상태

- 필터 결과가 0건이면 목록 영역에 `검색 결과가 없습니다` 또는 `해당 조건의 강사가 없습니다` 문구를 표시한다.
- 이 경우 기존 목록 대신 빈 결과 상태를 보여준다.

### 예외 상황

- 카테고리 값이 비어 있는 데이터가 일부 있어도 필터 기능 전체는 정상 동작해야 한다.
- 잘못된 카테고리 값이 들어온 경우 해당 항목은 `전체`에서만 노출하거나 제외할 수 있어야 한다.
- fallback 데이터 사용 중에도 필터는 동일하게 동작해야 한다.

### 이번 버전에서 확정한 디자인 판단

- 필터는 목록 상단에 가로로 배치한다.
- 각 카테고리는 칩 또는 버튼 형태로 표시한다.
- 현재 선택된 카테고리는 배경색 또는 테두리 차이로 분명히 구분한다.
- 기본값 `전체`는 항상 가장 앞에 배치한다.
- 카테고리 개수가 많아질 경우 한 줄 또는 여러 줄로 자연스럽게 배치하되, 이번 버전은 스크롤 없는 단순 구조를 우선한다.

### 구현 완료 기준

- 사용자가 카테고리를 선택하면 목록이 즉시 갱신된다.
- `전체`를 선택하면 전체 목록으로 돌아간다.
- 검색과 함께 사용해도 필터가 정상 동작한다.
- 정렬 상태를 유지한 채 필터가 적용된다.
- 현재 선택된 강사가 결과에 남아 있으면 선택 상태를 유지한다.
- 현재 선택된 강사가 결과에서 제외되면 선택 상태를 해제하고 상세 영역을 빈 상태로 전환한다.
- 필터 결과가 없으면 빈 상태 문구가 보인다.

### Feature D. 정렬

### 목적

사용자가 원하는 기준으로 강사 목록 순서를 바꿔볼 수 있어야 한다.
정렬은 현재 검색 및 필터 결과를 유지한 상태에서 목록의 우선순위만 다시 정하는 기능으로 동작해야 한다.

### 화면 위치

- 정렬 선택 영역은 강사 목록 상단에 배치한다.
- 카테고리 필터 오른쪽 또는 같은 상단 제어 영역 안에 배치한다.
- 사용자가 현재 어떤 기준으로 목록을 보고 있는지 쉽게 알 수 있어야 한다.

### 정렬 옵션

이번 버전에서 제공하는 정렬 기준은 아래와 같다.

- 점수순
- 순위순
- 출강순
- 최근 활동순
- 단가순
- 이름순

### 동작 방식

- 사용자가 정렬 기준을 변경하면 목록 결과가 즉시 다시 정렬되어야 한다.
- 정렬은 현재 검색어와 필터 조건을 유지한 상태에서 적용되어야 한다.
- 정렬은 목록의 순서만 바꾸며, 표시 정보 자체는 변경하지 않는다.

### 정렬 규칙

- 기본 정렬은 점수 높은 순으로 한다.
- 동일 값일 경우 tie-breaker는 순위 오름차순, 그다음 이름 오름차순으로 한다.
- 점수 정보가 없을 경우 다른 정렬 기준에 맞춰 처리하되, 비교 가능한 값이 없는 경우 이름순으로 밀린다.
- 이름순 정렬은 가나다순 기준으로 동작해야 한다.

### 검색 및 필터와의 관계

- 검색과 필터 결과가 먼저 적용된 뒤, 그 결과에 정렬이 적용되어야 한다.
- 정렬 변경 시 현재 검색어와 필터 상태는 그대로 유지되어야 한다.

### 예외 상황

- 일부 강사 데이터에 정렬 기준 값이 비어 있어도 정렬 기능 전체는 정상 동작해야 한다.
- 비교 가능한 값이 없는 항목은 목록 하단으로 보내거나 이름순 tie-breaker를 적용한다.
- fallback 데이터 사용 중에도 정렬은 동일하게 동작해야 한다.

### 이번 버전에서 확정한 디자인 판단

- 정렬은 드롭다운 형태로 제공한다.
- 기본 선택값은 `점수순`이다.
- 정렬 옵션은 한글 라벨로 표시한다.
- 정렬 UI는 검색창 및 필터와 시각적으로 같은 상단 제어 영역 안에 배치한다.

### 구현 완료 기준

- 사용자가 정렬 기준을 바꾸면 목록 순서가 즉시 변경된다.
- 검색과 필터 상태를 유지한 채 정렬이 동작한다.
- 동일 값일 경우 tie-breaker 규칙이 적용된다.
- fallback 상태에서도 정렬이 정상 동작한다.

### Feature E. 강사 상세 조회

### 목적

사용자가 목록에서 선택한 강사의 상세 정보를 같은 화면 안에서 바로 확인할 수 있어야 한다.
상세 조회는 강사 판단에 필요한 핵심 정보와 이력을 한 곳에서 보여주는 역할을 해야 한다.

### 화면 위치

- 상세 조회 영역은 화면 오른쪽 패널에 배치한다.
- 왼쪽 목록에서 강사를 클릭하면 오른쪽 상세 패널이 열려야 한다.
- 별도 페이지 이동은 하지 않는다.

### 동작 방식

- 사용자가 목록에서 강사를 클릭하면 해당 강사의 상세 정보가 오른쪽 패널에 표시되어야 한다.
- 상세 조회 중에는 로딩 상태를 보여줘야 한다.
- 다른 강사를 선택하면 상세 패널 내용이 즉시 교체되어야 한다.
- 첫 진입 시에는 상세 패널을 빈 상태로 둘 수 있다.

### 필수 표시 정보

상세 패널에는 최소 아래 정보가 보여야 한다.

- 이름
- 소속
- 연락처
- 카테고리
- 전문분야
- 강사 프로필 요약
- 총 출강 횟수
- 최근 6개월 활동
- 기본 단가 또는 단가 정보
- 강의 이력 요약

### 표시 규칙

- 값이 없는 항목은 `-`로 표시하거나 섹션 단위로 숨길 수 있다.
- 필수 정보가 일부 누락된 경우 `일부 데이터 누락` 배지를 표시한다.
- 상세 패널은 강사 1명 기준으로만 보여준다.
- 목록에서 현재 선택된 강사와 상세 패널의 대상은 항상 일치해야 한다.
- `profile_summary` 값이 있으면 상세 패널 상단의 기본 정보 영역에 표시한다.
- `profile_summary`는 이름 및 메타 정보 아래, 핵심 수치 위에 배치한다.
- `profile_summary`가 없으면 해당 영역은 숨긴다.
- 전임강사인 경우 상세 상단에서 `전임강사` 상태를 별도 배지로 표시한다.
- 전임강사의 시간당 강사료는 화면에서 직접 노출하지 않는다.
- 전임강사의 내부 fee 값은 관리할 수 있지만, 사용자 화면에서는 `전임강사` 상태만 표시한다.

### 빈 상태 및 오류 상태

- ID에 해당하는 강사가 없으면 `강사 정보를 찾을 수 없습니다` 문구를 표시한다.
- 상세 조회 API 실패 시 fallback 데이터를 이용해 조회를 시도한다.
- fallback 조회도 실패하면 상세 패널을 빈 상태 또는 오류 상태로 표시한다.
- 오류가 발생해도 목록 영역은 유지되어야 한다.

### 이번 버전에서 확정한 디자인 판단

- 상세 조회는 우측 고정 패널 구조로 제공한다.
- 패널 상단에는 강사 이름과 핵심 메타 정보를 우선 배치한다.
- 상세 패널 내부는 위에서 아래로 요약 정보, 이력, 메모 순서로 구성한다.
- 상세 패널은 목록과 독립적으로 스크롤된다.

### 구현 완료 기준

- 강사 클릭 시 상세 패널이 열린다.
- 필수 정보가 표시된다.
- 일부 필드가 누락되어도 화면이 깨지지 않는다.
- 잘못된 ID 또는 조회 실패 시 오류 또는 빈 상태가 표시된다.
- fallback 데이터가 있으면 상세 조회가 계속 가능하다.

### Feature F. 핵심 수치 표시

### 목적

상세 화면 상단에서 강사 판단에 필요한 핵심 요약값을 한눈에 보여줘야 한다.
사용자는 상세 데이터를 읽기 전에 먼저 강사의 활동 규모와 단가 상태를 빠르게 파악할 수 있어야 한다.

### 화면 위치

- 핵심 수치 영역은 상세 패널 상단, 기본 정보 아래에 배치한다.
- 강사 상세 화면에서 가장 먼저 확인하는 요약 영역으로 제공한다.

### 표시 항목

이번 버전에서 표시하는 핵심 수치는 아래와 같다.

- 총 출강 횟수
- 최근 6개월 출강 횟수
- 대표 출강 단가
- 단가 변동

### 표시 규칙

- 총 출강 횟수는 `N회` 형식으로 표시한다.
- 최근 6개월 출강 횟수도 동일하게 `N회` 형식으로 표시한다.
- 대표 출강 단가는 `teaching_history.deal_fee_hourly` 유효값의 최빈값을 기준으로 계산한다.
- 단가 변동은 `fee_history`를 기준으로 계산한다.
- 단가 변동 기록이 없으면 `변동 없음`으로 표시한다.
- 값이 없는 경우 `-` 또는 기본 표현을 사용한다.

### 예외 상황

- 일부 수치 계산에 필요한 원본 데이터가 없더라도 나머지 수치는 정상적으로 보여야 한다.
- 대표 출강 단가를 계산할 수 없는 경우 해당 항목만 `-`로 표시한다.
- fallback 상태에서도 동일한 형식으로 표시되어야 한다.

### 이번 버전에서 확정한 디자인 판단

- 핵심 수치는 카드형 요약 블록 4개로 배치한다.
- 각 카드에는 항목명과 값을 함께 표시한다.
- 데스크톱에서는 4개 수치를 한 줄로 배치한다.
- 숫자는 값이 가장 눈에 띄도록 강조한다.

### 구현 완료 기준

- 상세 패널 상단에 4개 핵심 수치가 보인다.
- 대표 출강 단가와 단가 변동이 정의된 계산 규칙에 따라 표시된다.
- 일부 수치 데이터가 없어도 화면이 깨지지 않는다.
- fallback 상태에서도 동일한 구조로 노출된다.

### Feature G. 점수 구성 요소 및 만족도 표시

### 목적

상세 화면에서 강사의 종합 점수와 만족도 정보를 함께 확인할 수 있어야 한다.
사용자는 점수 자체뿐 아니라 어떤 요소로 점수가 구성되는지도 이해할 수 있어야 한다.

### 화면 위치

- 점수 구성 요소 및 만족도 영역은 상세 패널 내 핵심 수치 영역 아래, 강의 이력 위에 배치한다.
- 핵심 수치를 확인한 뒤 점수의 근거를 자연스럽게 이어서 볼 수 있어야 한다.

### 표시 항목

- 종합 점수
- 점수 구성 요소 (ScoreBreakdown 7개 항목)
- 만족도 점수
- 만족도 관련 보조 정보가 있으면 함께 표시

### 동작 방식

- 점수 값이 있으면 종합 점수를 표시한다.
- 점수 구성 요소 값이 있으면 항목별 구성 정보를 함께 표시한다.
- 만족도 값이 있으면 함께 표시한다.
- 만족도가 중앙값 대체인 경우(`is_imputed: true`) 해당 사실을 표시한다.
- 점수 또는 만족도 데이터가 없으면 해당 항목만 숨기거나 `-`로 표시할 수 있다.

### 표시 규칙

- 점수는 사용자가 한눈에 볼 수 있도록 강조된 숫자로 표시한다.
- 점수 구성 요소는 항목별 점수와 만점을 함께 표시한다.
  - 예: `출강횟수 28/35`, `만족도 13.9/15`
- 만족도는 0~5 범위 기준으로 표시한다.
- 종합 점수는 있어도 점수 구성 요소가 없을 수 있다.
- 만족도는 있어도 종합 점수와 독립적으로 표시할 수 있다.

### 예외 상황

- 점수 데이터가 없더라도 상세 화면 전체는 정상적으로 보여야 한다.
- 점수 구성 요소 일부가 비어 있어도 표시 가능한 항목만 보여준다.
- 만족도 데이터가 없으면 만족도 영역은 숨기거나 `-`로 표시한다.
- fallback 상태에서도 사용 가능한 범위의 점수와 만족도를 표시한다.

### 이번 버전에서 확정한 디자인 판단

- 종합 점수는 카드 또는 강조 숫자 형태로 보여준다.
- 점수 구성 요소는 리스트형 또는 막대형으로 표시하되, 항목 구분이 명확해야 한다.
- 만족도는 종합 점수와 가까운 위치에서 함께 보여준다.
- 점수와 만족도는 강의 이력보다 상단에 배치한다.

### 구현 완료 기준

- 종합 점수가 있을 경우 상세 화면에서 확인할 수 있다.
- 점수 구성 요소가 있을 경우 항목별로 표시된다.
- 만족도 데이터가 있을 경우 함께 표시된다.
- 만족도가 중앙값 대체인 경우 해당 사실이 표시된다.
- 점수 또는 만족도 일부가 없어도 화면이 깨지지 않는다.

### Feature H. 운영 인텔리전스 표시

### 목적

운영 판단에 필요한 추천, 지양, 리스크, 확인 필요 사항을 상세 화면에서 확인할 수 있어야 한다.
사용자는 수치 정보 외에도 운영 관점의 판단 보조 정보를 함께 볼 수 있어야 한다.

### 화면 위치

- 운영 인텔리전스 영역은 상세 패널 내 점수 및 만족도 영역 아래, 강의 이력 위 또는 인접한 위치에 배치한다.
- 사용자가 강사의 정량 정보와 정성 정보를 함께 읽을 수 있어야 한다.

### 표시 항목

- 추천 대상
- 지양 대상
- 리스크 정보
- 운영 확인 필요 사항

### 동작 방식

- 추천 대상 정보가 있으면 표시한다.
- 지양 대상 정보가 있으면 표시한다.
- 추천 대상과 지양 대상 정보는 노션에 입력된 값을 기준으로 노출한다.
- 이번 버전에서는 추천/지양 정보를 자동 생성하지 않는다.

### 표시 규칙

- 추천 대상과 지양 대상은 구분된 형태로 보여야 한다.
- 리스크 정보는 일반 정보와 구분되는 강조 표현이 필요하다.
- 운영 확인 필요 사항은 별도 섹션 또는 강조 박스로 보여야 한다.
- 값이 없는 항목은 숨길 수 있다.

### 예외 상황

- 운영 인텔리전스 데이터가 없더라도 상세 화면 전체는 정상적으로 보여야 한다.
- 일부 항목만 존재하는 경우 해당 항목만 선택적으로 표시한다.
- fallback 상태에서도 사용 가능한 운영 인텔리전스 정보가 있으면 표시한다.

### 이번 버전에서 확정한 디자인 판단

- 추천 대상과 지양 대상은 태그 또는 배지 형태로 구분해 보여준다.
- 리스크 정보는 경고성 정보로 인식할 수 있게 표시한다.
- 운영 확인 필요 사항은 별도 카드 또는 강조 영역으로 배치한다.
- 운영 인텔리전스는 메모와 구분되는 구조화된 정보 영역으로 제공한다.

### 구현 완료 기준

- 추천 대상, 지양 대상, 리스크, 운영 확인 필요 사항이 있을 경우 상세 화면에 표시된다.
- 값이 일부만 있어도 해당 정보만 선택적으로 노출된다.
- 데이터가 없어도 화면이 깨지지 않는다.

### Feature I. 강의 이력 표시

### 목적

강사의 실제 출강 이력을 표 형태로 제공해, 사용자가 강사의 활동 내역을 구체적으로 확인할 수 있어야 한다.

### 화면 위치

- 강의 이력은 상세 패널 내 운영 인텔리전스 영역 아래에 배치한다.
- 사용자가 강사의 실제 활동 내역을 읽을 수 있는 주요 정보 영역으로 제공한다.

### 표시 항목

- 기업명
- 과정명
- 일정
- 출강 단가
- 특이사항

### 동작 방식

- 강의 이력은 최신순으로 정렬해 보여준다.
- 유효하지 않은 행은 표시 대상에서 제외한다.
- 최근 30건까지 노출한다.
- 30건을 초과하면 `N건 더 있음` 문구를 하단에 표시한다.

### 표시 규칙

- 날짜 기준으로 최신 이력이 먼저 보이도록 정렬한다.
- 출강 단가가 없으면 `-`로 표시한다.
- 특이사항이 없으면 빈칸 또는 `-`로 표시한다.
- 텍스트가 너무 길 경우 표 안에서 말줄임 또는 제한 길이로 처리한다.

### 빈 상태

- 강의 이력이 없으면 `강의 이력이 없습니다` 문구를 표시한다.
- 이 경우 표 대신 빈 상태 영역을 보여준다.

### 예외 상황

- 일부 이력 행의 필드가 비어 있어도 전체 이력 표는 정상적으로 보여야 한다.
- 날짜가 불완전한 경우 정렬 가능한 범위 내에서 처리하고, 불가능하면 하단으로 보낸다.
- fallback 상태에서도 동일한 구조로 이력을 보여준다.

### 이번 버전에서 확정한 디자인 판단

- 강의 이력은 표 형태로 제공한다.
- 헤더 행은 고정된 컬럼명으로 구성한다.
- 최신순 정렬을 기본으로 한다.
- 표는 상세 패널 폭 안에서 읽기 쉬운 밀도로 구성한다.

### 구현 완료 기준

- 강의 이력이 1건 이상이면 표로 노출된다.
- 최신순 정렬이 적용된다.
- 30건 초과 시 추가 건수 안내가 표시된다.
- 이력이 없을 경우 빈 상태 문구가 보인다.
- 일부 필드 누락이 있어도 표 전체가 깨지지 않는다.

### Feature J. 단가 이력 표시

### 목적

강사의 단가 또는 강사료 변동 이력을 보여줘, 사용자가 현재 단가 수준과 변화 흐름을 파악할 수 있어야 한다.

### 화면 위치

- 단가 이력은 상세 패널 내 강의 이력 아래에 배치한다.
- 강의 이력과 구분되지만 함께 확인하기 쉬운 영역에 둔다.

### 표시 항목

- 날짜
- 금액
- 변경 사유 또는 컨텍스트
- 출처

### 동작 방식

- 단가 이력은 최신순으로 정렬해 보여준다.
- 이력이 존재할 경우에만 섹션을 노출한다.
- 이력이 없으면 섹션을 숨기거나 `이력 없음` 문구를 표시한다.

### 표시 규칙

- 날짜가 최신인 항목이 먼저 보이도록 한다.
- 금액은 일관된 금액 포맷으로 표시한다.
- 변경 사유가 없으면 `-`로 표시한다.
- 출처가 있으면 함께 표시한다.
- 비정상 변동값은 검증 단계에서 제외할 수 있다.
- 전임강사 여부는 단가 자체와 별도로 관리하며, 단가 이력 화면에서도 필요 시 `전임강사` 상태를 함께 표시할 수 있다.

### 예외 상황

- 일부 이력 항목의 필드가 비어 있어도 나머지 이력은 정상적으로 보여야 한다.
- 최신순 정렬이 어려운 데이터는 하단으로 보낼 수 있다.
- fallback 상태에서도 가능한 범위의 단가 이력을 보여줘야 한다.

### 이번 버전에서 확정한 디자인 판단

- 단가 이력은 타임라인형 블록으로 제공한다.
- 각 이력 항목은 날짜, 금액, 설명이 한 묶음으로 읽히게 구성한다.
- 최근 변화가 먼저 보이도록 상단에 배치한다.

### 구현 완료 기준

- `fee_history`가 있을 때 섹션이 노출된다.
- 최신순 정렬이 적용된다.
- 값 일부가 비어 있어도 섹션이 깨지지 않는다.
- 이력이 없으면 숨김 또는 `이력 없음` 처리가 된다.

### Feature K. 운영 메모 표시

### 목적

운영 판단에 필요한 메모를 상세 화면에서 확인할 수 있어야 한다.
운영 메모는 수치 정보만으로 알기 어려운 맥락을 보완하는 역할을 해야 한다.

### 화면 위치

- 운영 메모는 상세 패널 하단 영역에 배치한다.
- 강의 이력과 단가 이력 아래에서 추가 참고 정보로 제공한다.

### 동작 방식

- 메모가 있는 경우에만 섹션을 노출한다.
- 메모가 없으면 섹션을 숨긴다.

### 표시 규칙

- 메모는 원문 기반으로 표시한다.
- 민감정보는 검증 단계에서 마스킹 후 노출한다.
- 메모가 너무 길 경우에도 문단 단위로 읽을 수 있게 표시한다.
- 줄바꿈이 있는 경우 가능한 한 원문 구조를 유지한다.

### 예외 상황

- 메모가 비어 있으면 섹션을 노출하지 않는다.
- 민감정보가 포함된 경우 원문 전체를 그대로 노출하지 않는다.
- fallback 상태에서도 사용 가능한 메모가 있으면 동일한 방식으로 표시한다.

### 이번 버전에서 확정한 디자인 판단

- 운영 메모는 별도의 카드 또는 박스 형태로 구분해 보여준다.
- 다른 정량 정보와 달리 문장형 텍스트 영역으로 제공한다.
- 화면 하단 참고 정보 영역으로 배치한다.

### 구현 완료 기준

- 메모가 존재하면 상세 하단에 표시된다.
- 민감정보 마스킹 규칙이 반영된다.
- 메모가 없어도 화면이 깨지지 않는다.

### Feature L. 데이터 상태 및 새로고침

### 목적

현재 데이터가 얼마나 최신인지, 그리고 사용자가 최신 데이터로 갱신할 수 있는지 알 수 있어야 한다.

### 화면 위치

- 데이터 상태 정보는 목록 영역 상단 또는 공통 상단 메타 영역에 배치한다.
- 새로고침 버튼은 이 영역 안에서 함께 제공한다.

### 표시 항목

- 마지막 업데이트 시각
- 소스별 연결 상태
- 소스별 최근 수집 시각
- 새로고침 버튼

### 동작 방식

- 사용자가 새로고침 버튼을 누르면 최신 데이터 갱신을 시도해야 한다.
- 새로고침 중에는 버튼을 비활성화해야 한다.
- 새로고침 성공 시 목록과 상세 데이터를 다시 조회한다.
- 새로고침 실패 시 기존 데이터는 유지한다.

### 표시 규칙

- 마지막 업데이트 시각은 사람이 읽기 쉬운 형태로 표시한다.
- 소스별 연결 상태가 있으면 성공, 실패, 미연결을 구분할 수 있어야 한다.
- 새로고침 중에는 로딩 상태를 표시한다.
- 실패 시 토스트 또는 배너로 안내한다.

### 예외 상황

- 일부 데이터 소스만 실패해도 사용 가능한 데이터는 유지해야 한다.
- 새로고침 실패 후에도 기존 목록과 상세는 계속 사용할 수 있어야 한다.
- fallback 상태에서는 fallback 사용 중임을 함께 안내해야 한다.

### 이번 버전에서 확정한 디자인 판단

- 데이터 상태는 상단 메타 정보 줄에 compact하게 배치한다.
- 새로고침 버튼은 아이콘 버튼 또는 짧은 버튼 형태로 제공한다.
- 실패나 fallback 상태는 배너 또는 강조 문구로 명확히 보여준다.

### 구현 완료 기준

- 새로고침 클릭 시 로딩 상태가 보인다.
- 성공 시 최신 시각이 갱신된다.
- 실패 시 기존 데이터가 유지된다.
- 소스 상태 또는 fallback 상태를 사용자에게 안내할 수 있다.

### Feature M. fallback 처리

### 목적

API 또는 일부 데이터 소스에 문제가 있어도 사용자가 기본 기능을 계속 사용할 수 있어야 한다.

### 동작 방식

- 데이터 조회는 아래 순서로 시도한다.
  - `live API -> cached/master dataset -> fallback dataset`
- 상위 단계가 실패하면 다음 단계 데이터를 사용한다.
- fallback 데이터로 전환된 경우 사용자에게 현재 상태를 안내해야 한다.

### 적용 범위

- 강사 목록 조회
- 검색
- 필터
- 정렬
- 강사 상세 조회

### 표시 규칙

- fallback 사용 시 상단에 `임시 데이터 표시 중` 안내를 표시한다.
- fallback 상태에서도 목록과 상세 조회는 정상적으로 동작해야 한다.
- fallback 상태에서는 일부 최신 정보가 없을 수 있음을 알릴 수 있어야 한다.

### 예외 상황

- live API와 fallback 데이터 모두 실패하면 빈 상태 또는 오류 상태를 보여준다.
- fallback 데이터가 일부 필드를 포함하지 않아도 화면 전체는 깨지지 않아야 한다.

### 이번 버전에서 확정한 디자인 판단

- fallback 안내는 상단 배너 형태로 표시한다.
- 배너는 현재 사용자가 임시 데이터를 보고 있음을 명확히 전달해야 한다.
- 목록과 상세 영역은 fallback 여부와 관계없이 동일한 구조를 유지한다.

### 구현 완료 기준

- API가 실패해도 화면이 깨지지 않는다.
- fallback 데이터가 있으면 서비스가 계속 동작한다.
- 사용자에게 fallback 상태가 명확히 보인다.
- fallback 상태에서도 검색, 정렬, 상세 조회가 가능하다.

### Feature N. 마스터 데이터 수집/병합 결과 조회

### 목적

여러 운영 데이터 소스를 병합한 결과를 단일 강사 기준 데이터로 조회할 수 있어야 한다.
프론트엔드는 여러 원본 소스를 직접 다루지 않고, 병합된 마스터 레코드를 기준으로 화면을 구성해야 한다.

### 범위

- 이번 버전은 병합 엔진 자체 구현보다 `병합 결과를 읽는 구조`를 우선한다.
- 실시간 병합은 제외 가능하다.
- 배치 또는 사전 생성된 마스터 데이터 사용을 허용한다.

### 데이터 소스 후보

- 계약시트
- 노션
- 세일즈맵
- 지메일
- 슬랙

### 동작 방식

- 프론트엔드는 단일 형태의 마스터 레코드를 받아 목록과 상세를 렌더링한다.
- 일부 소스가 실패해도 마스터 레코드가 존재하면 조회는 가능해야 한다.
- 병합 결과는 강사 1명당 1개의 기준 레코드 형태여야 한다.

### 규칙

- 소스 우선순위는 별도 설정 파일 또는 상수로 관리한다.
- 추측 매칭은 허용하지 않는다.
- 병합 결과는 `master instructor record`를 기준으로 사용한다.
- 프론트엔드는 원본 데이터 소스 구조에 의존하지 않는다.

### 예외 상황

- 일부 소스 데이터가 누락돼도 마스터 레코드가 유효하면 조회를 허용한다.
- 병합 결과가 불완전한 경우 일부 필드는 빈값으로 처리하되 전체 레코드는 사용할 수 있어야 한다.

### 이번 버전에서 확정한 디자인 판단

- 이 기능은 사용자에게 직접 보이는 UI 기능이 아니라 내부 데이터 구조 기준으로 정의한다.
- 사용자 화면에는 원본 소스별 구조 대신 병합된 결과만 노출한다.

### 구현 완료 기준

- 프론트는 단일 형태의 마스터 레코드를 받는다.
- 소스가 일부 실패해도 마스터 레코드가 존재하면 조회 가능하다.
- 화면 구현이 원본 데이터 소스 구조에 직접 의존하지 않는다.

## 8. 데이터 병합 규칙

- 기본 병합 기준은 `instructor_id`다.
- 동일한 `instructor_id`를 가진 데이터는 동일 강사로 간주하고 우선 병합한다.
- `instructor_id`가 없는 경우에는 강사명을 기준으로 병합 후보를 찾는다.
- 이름 기반 병합 시에는 연락처 정보를 함께 비교해 동일 인물 여부를 검증한다.
- 연락처 비교 항목은 전화번호와 이메일을 우선 사용한다.
- alias 매핑은 사용하지 않는다.
- 이름은 exact match 기준으로만 비교한다.
- 서로 다른 이름은 서로 다른 강사로 간주한다.
- 동명이인이 있는 경우에는 이름 끝에 식별 문자를 붙여 구분한다.
  - 예: `홍길동`, `홍길동B`
- 동명이인 구분이 적용된 이름은 서로 다른 강사로 간주한다.
- `course_id`와 소속 정보가 있는 경우에는 보조 검증 정보로 활용한다.
- 전임강사 여부는 별도 전임강사 리스트 기준으로 관리한다.
- 서로 다른 데이터 소스 간 값이 충돌할 경우 우선순위는 `계약시트 > 노션 > 세일즈맵 > 지메일/슬랙`을 따른다.

## 9. 데이터 검증 규칙

시스템은 화면에 데이터를 노출하기 전에 아래 기준으로 기본 검증을 수행해야 한다.

### 9-1. 수치 검증

- 강사료는 0 이상이어야 한다.
- 일반 강사의 강사료는 50,000원~500,000원 범위를 벗어나면 경고를 표시한다. 전임강사는 이 범위 검증에서 제외한다.
- base_fee와 최빈 출강 단가의 차이가 2배 이상이면 경고를 표시한다.
- 만족도는 0~5 범위 안에 있어야 한다.
- 총 출강 횟수와 최근 6개월 출강 횟수는 음수가 될 수 없다.

### 9-2. 연락처 검증

- 전화번호와 이메일은 기본 형식 검증을 수행해야 한다.
- 형식이 올바르지 않은 경우 원문을 그대로 신뢰하지 않고, 검토 대상 또는 빈값 처리할 수 있어야 한다.

### 9-3. 단가 및 이력 검증

- 강사료 변동이 3배 이상이거나 특수비용(콘텐츠 제작비 등)이 포함된 경우 자동 수정으로 제거한다.
- 비정상적으로 보이는 단가 변동은 자동 제외하지 않고 우선 검토 대상으로 표시한다.
- 강사료 이력과 강의 이력 간에 명백한 충돌이 있는 경우 검토 대상으로 남길 수 있어야 한다.
- 전임강사, 특수 계약 건, 내부 정산 기준이 적용된 데이터는 일반 강사와 동일한 규칙으로 단정하지 않는다.
- 콘텐츠 제작비, 건당 금액, 출장비 포함 금액 등은 일반 시간당 강사료와 분리해서 해석해야 한다.
- 특수 금액은 `base_fee_hourly` 계산에 직접 사용하지 않는다.
- 강사료 변동 이력은 시간순으로 자동 정렬한다.
- fee_history의 "현재" 금액과 base_fee_hourly가 불일치하면 자동 수정한다.

### 9-4. 이력 정합성 검증

- total_courses는 teaching_history의 유효 행 수 기준으로 재계산한다.
- recent_courses_6mo는 teaching_history의 날짜 기준으로 재계산한다.
- teaching_history에서 company+course+dates 키가 동일한 중복 행은 자동 제거한다.
- contract_sheet_rows와 teaching_history(source=contract_sheet) 수가 불일치하면 경고를 표시한다.
- 날짜 형식은 YYYY-MM-DD로 자동 정규화한다.

### 9-5. 문자열 정제

- 기업명과 과정명에 포함된 불필요한 접두사(`[부가세별도]`, `(B2B)` 등), 노이즈, 중복 텍스트는 자동 제거한다.
- 비고에서 행정정보(사업자번호, 계약서 링크 등)는 자동 제거한다.
- 운영노트에서 계약정보는 자동 제거한다.
- 운영 메모 및 텍스트 필드에 포함된 민감정보 문자열은 마스킹 후 노출해야 한다.

### 9-6. 운영 예외 보존

- 전임 강사, 실습코치, 특수 계약 여부와 같은 운영상 중요한 플래그는 정제 과정에서 제거하지 않고 유지해야 한다.
- 실습코치 flag와 score=0의 정합성을 검증하고, 불일치 시 자동 수정한다.
- 자동발견된 강사의 category/specialties가 빈칸이면 경고를 표시한다.
- 이력 50건 이상인데 Engagement Score가 30 미만이면 역전 경고를 표시한다.

### 9-7. 검증 결과 처리

- 검증 실패 항목이 있더라도 전체 화면이 깨지지 않아야 한다.
- 경미한 문제는 빈값 또는 경고 상태로 처리할 수 있어야 한다.
- 중요한 충돌이나 의심 데이터는 운영 검토 대상으로 남길 수 있어야 한다.
- 자동 수정이 적용된 항목은 수정 내역을 기록한다.

## 10. 이벤트 로그

### 10-1. 목록 및 탐색 이벤트

- `dashboard_viewed`: 대시보드 첫 진입 시 기록한다.
- `search_changed`: 사용자가 검색어를 입력해 목록 결과가 갱신될 때 기록한다.
- `filter_changed`: 사용자가 카테고리 필터를 변경할 때 기록한다.
- `sort_changed`: 사용자가 정렬 기준을 변경할 때 기록한다.

### 10-2. 상세 조회 이벤트

- `instructor_selected`: 사용자가 목록에서 특정 강사를 선택할 때 기록한다.
- `detail_loaded`: 상세 조회가 성공하고 필수 정보가 정상적으로 렌더링된 경우 기록한다.
- `detail_partial`: 상세 조회는 되었지만 필수 정보 일부가 누락된 경우 기록한다.
- `detail_error`: 상세 조회 자체가 실패하거나 상세 패널이 렌더링되지 않은 경우 기록한다.

### 10-3. 데이터 갱신 이벤트

- `refresh_clicked`: 사용자가 새로고침 버튼을 눌렀을 때 기록한다.
- `refresh_succeeded`: 새로고침이 성공해 최신 데이터가 반영되었을 때 기록한다.
- `refresh_failed`: 새로고침이 실패했을 때 기록한다.

### 10-4. fallback 이벤트

- `fallback_used`: live API 대신 cached/master dataset 또는 fallback dataset을 사용하게 된 경우 기록한다.

### 10-5. 이벤트 기록 원칙

- 이벤트 로그는 성공 지표 및 기본 사용 패턴 분석에 활용할 수 있어야 한다.
- 이벤트 이름은 일관된 규칙으로 유지해야 한다.
- 동일 동작에 대해 중복 로그가 과도하게 쌓이지 않도록 제어해야 한다.

## 11. 점수 정책

### 11-1. Engagement Score 산정 방식

- Engagement Score는 현재 병합된 강사 데이터를 기준으로 계산한다.
- 총점은 100점 만점이다.
- 점수는 아래 7개 요소로 계산한다.
  - 출강횟수: 35점
  - 만족도: 15점
  - 슬랙 활동: 15점
  - 최근성: 15점
  - 세일즈맵 딜: 10점
  - 이메일 활동: 5점
  - 운영 채널 활동: 5점

### 11-2. 계산 규칙

- 출강횟수, 슬랙 활동, 세일즈맵 딜, 이메일 활동, 운영 채널 활동은 전체 강사 중 최대값 대비 비율로 정규화한다.
- 정규화 최대값은 동적이다. 강사 추가 또는 이력 추가 시 최대값이 바뀌면 전원 점수를 재계산한다.
- 만족도는 `avg_score / 5.0` 기준으로 계산한다.
- 만족도 데이터가 없으면 전체 수집 강사의 중앙값을 대체값으로 사용한다.
- 만족도 중앙값도 동적이다. 만족도 수집 강사 수가 변하면 중앙값이 변동한다.
- 최근성은 최근 활동일 기준 지수 감쇠 방식으로 계산한다. 감쇠 상수는 180일이다.
- 최근 활동일은 슬랙, 세일즈맵, 지메일 중 가장 최근 날짜를 사용한다.
- 최근 활동일이 없으면 최근성 점수는 0점이다.
- 실습코치로 분류된 강사는 Engagement Score를 0점으로 처리한다.

### 11-3. 실습코치 판정 기준

실습코치 여부는 아래 3단계 로직으로 판정한다.

- L1 계약유형 비율: 계약시트에서 해당 강사의 계약 유형 중 '보조강사/코치/실습코치/멘토/문항개발' 비율이 정규강사 비율보다 높으면 실습코치 후보로 분류한다.
- L2 프로필 보호: 후보 중 시간당 강사료가 100,000원 이상이고 category와 specialties가 모두 있으면 후보에서 제외한다. (정규강사로 보호)
- L3 전임강사 보호: 전임강사 목록에 포함된 강사는 무조건 후보에서 제외한다.

실습코치로 최종 판정된 강사는 `flag='실습코치'`, `engagement_score=0`으로 처리한다.

### 11-4. 점수 표시 규칙

- 상세 화면에서는 종합 점수와 점수 구성 요소를 함께 표시한다.
- 점수 구성 요소는 각 항목별 점수와 만점으로 보여준다.

## 12. fee 결정 정책

### 12-1. 일반 강사 fee 결정 소스 우선순위

일반 강사(전임강사가 아닌 강사)의 `base_fee_hourly`는 아래 우선순위에 따라 결정한다.

```
1순위: fee_fixes (수동 보정값, 별도 설정 파일로 관리)
2순위: 노션 DB fee_note
3순위: 세일즈맵 딜에서 확인된 금액
4순위: 계약시트 col T (시간당 강사료 원본)
```

- fee_fixes는 코드에 하드코딩하지 않고 별도 설정 파일로 관리한다.
- 상위 순위 소스에서 값이 확인되면 하위 순위는 확인하지 않는다.
- 모든 소스에서 확인되지 않으면 `base_fee_hourly`는 `-`로 처리한다.

### 12-2. 전임강사 fee 결정

- 전임강사의 fee는 위 일반 강사 우선순위를 따르지 않는다.
- 전임강사의 `base_fee_hourly`는 노션에 기재된 기본 강사료 또는 fee_note를 기준으로 사용한다.
- 노션에 시간당 강사료가 명확하지 않으면 `base_fee_hourly`는 `NULL`로 둔다.
- 전임강사라고 해서 시간당 강사료를 자동으로 0원 처리하지 않는다.

### 12-3. 전임강사 화면 표시 규칙

- 전임강사는 화면에서 `전임강사` 배지 또는 상태값으로 별도 표시한다.
- 전임강사의 시간당 강사료는 노션 기준 값이 있더라도 화면에서 직접 노출하지 않는다.
- API 응답에서는 전임강사의 `base_fee_hourly`를 `null`로 반환하고, 화면에는 전임강사 상태만 노출한다.

### 12-4. 전임강사 관리

- 전임강사 여부는 별도 전임강사 리스트를 기준으로 판단한다.
- 전임강사 여부와 시간당 강사료는 서로 다른 속성으로 관리한다.
- `is_fulltime` 또는 동등한 상태값으로 관리한다.

## 13. 성공 지표

### 13-1. 강사 상세 정보 조회 성공률

- 목적: 사용자가 강사 상세 화면을 열었을 때 핵심 정보가 정상적으로 표시되는지 확인한다.
- 정의: 상세 화면 로드시 필수 정보가 정상적으로 렌더링된 비율
- 필수 정보:
  - `name`
  - `affiliation`
  - `category`
  - `total_courses`
  - `base_fee_hourly`
- 성공 조건: 위 필수 정보가 모두 존재하고, 상세 패널이 오류 없이 정상 렌더링되어야 한다.
- 부분 성공 조건: 상세 패널은 열리지만 필수 정보 중 일부가 누락된 경우 `partial` 상태로 본다.
- 실패 조건: 상세 조회 자체가 실패하거나, 상세 패널이 렌더링되지 않는 경우 `error` 상태로 본다.
- 계산식: `detail_loaded / (detail_loaded + detail_partial + detail_error)`
- 목표: 95% 이상

### 13-2. 점수 구성 요소 표시 성공률

- 목적: 종합 점수뿐 아니라 점수 구성 요소가 사용자에게 정상적으로 보이는지 확인한다.
- 정의: 종합 점수가 있는 강사 중 점수 구성 요소가 함께 표시된 비율
- 성공 조건: `score`와 `score_breakdown`이 함께 표시된다.
- 목표: 95% 이상

### 13-3. 운영 인텔리전스 표시 성공률

- 목적: 추천/지양/리스크/운영 확인 필요 사항이 있는 강사에 대해 해당 정보가 정상적으로 보이는지 확인한다.
- 정의: 운영 인텔리전스 데이터가 존재하는 강사 중 화면에 정상 노출된 비율
- 목표: 95% 이상

## 14. 테스트 포인트

### 14-1. 목록 및 탐색

- 목록이 최초 진입 시 정상적으로 로드되는지 확인한다.
- 검색, 필터, 정렬을 함께 사용해도 목록이 정상적으로 갱신되는지 확인한다.
- 검색 결과가 없을 때 빈 상태 문구가 정상적으로 보이는지 확인한다.

### 14-2. 상세 조회

- 목록에서 강사를 클릭하면 상세 패널이 정상적으로 열리는지 확인한다.
- 상세 조회 시 필수 정보가 정상적으로 표시되는지 확인한다.
- 필드 일부가 누락된 경우 `partial` 상태가 정상적으로 처리되는지 확인한다.
- 존재하지 않는 강사 ID 또는 잘못된 데이터일 때 오류 상태가 정상적으로 표시되는지 확인한다.
- `profile_summary`가 있을 때 상세 상단에 정상적으로 표시되는지 확인한다.

### 14-3. 점수 및 만족도

- 종합 점수가 있을 때 정상적으로 표시되는지 확인한다.
- 점수 구성 요소가 있을 때 7개 항목별 정보가 정상적으로 표시되는지 확인한다.
- 만족도 데이터가 있을 때 정상적으로 표시되는지 확인한다.
- 만족도가 중앙값 대체인 경우 `is_imputed` 표시가 정상적으로 동작하는지 확인한다.
- 만족도 데이터가 없을 때 빈값 또는 대체 규칙이 정상적으로 적용되는지 확인한다.

### 14-4. 운영 인텔리전스

- 추천 대상 정보가 있을 때 정상적으로 표시되는지 확인한다.
- 지양 대상 정보가 있을 때 정상적으로 표시되는지 확인한다.
- 리스크 정보가 있을 때 강조된 형태로 정상적으로 표시되는지 확인한다.
- 운영 확인 필요 사항이 있을 때 별도 영역으로 표시되는지 확인한다.

### 14-5. 이력 및 메모

- 강의 이력이 있을 때 표가 최신순으로 표시되는지 확인한다.
- 강의 이력이 최근 30건 기준으로 노출되는지 확인한다.
- 강의 이력이 0건일 때 빈 상태 문구가 정상적으로 보이는지 확인한다.
- 단가 이력이 최신순으로 표시되는지 확인한다.
- 운영 메모가 있을 때 상세 하단에 정상적으로 표시되는지 확인한다.

### 14-6. 전임강사 fee 처리

- 전임강사 fee가 내부 데이터에 존재해도 화면에 직접 노출되지 않는지 확인한다.
- API 응답에서 전임강사의 `base_fee_hourly`가 `null`로 내려오는지 확인한다.
- 건당 금액, 콘텐츠 제작비, 특수 비용이 일반 시간당 단가로 잘못 표시되지 않는지 확인한다.

### 14-7. 실습코치 처리

- 실습코치로 판정된 강사의 Engagement Score가 0점인지 확인한다.
- 실습코치 판정 3-Layer 로직이 정상 동작하는지 확인한다.
- 프로필 보호 대상(fee≥100K, 프로필 보유)이 실습코치에서 제외되는지 확인한다.
- 전임강사 목록 대상이 실습코치에서 제외되는지 확인한다.

### 14-8. 데이터 검증

- 강사료 범위 경고가 정상 동작하는지 확인한다.
- teaching_history 중복 제거가 정상 동작하는지 확인한다.
- 날짜 형식 정규화가 정상 동작하는지 확인한다.
- 자동수정 항목의 수정 내역이 기록되는지 확인한다.

### 14-9. 데이터 상태 및 갱신

- 새로고침 성공 시 목록과 상세 데이터가 갱신되는지 확인한다.
- 새로고침 실패 시 기존 데이터가 유지되는지 확인한다.
- 마지막 업데이트 시각 및 상태 정보가 정상적으로 표시되는지 확인한다.

### 14-10. fallback 및 예외 처리

- API 실패 시 fallback 데이터로 정상 전환되는지 확인한다.
- fallback 상태에서도 목록, 검색, 정렬, 상세 조회가 가능한지 확인한다.
- 일부 데이터가 누락되어도 전체 화면이 깨지지 않는지 확인한다.
