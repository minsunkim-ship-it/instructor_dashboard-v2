## 1. 화면 개요

- 서비스는 데스크톱 우선 내부 운영 대시보드다.
- 기본 레이아웃은 `좌측 목록 + 우측 상세 패널` 구조를 사용한다.
- 첫 진입 시 상세 패널은 빈 상태로 두고, 사용자가 목록에서 강사를 선택한 뒤에만 상세를 연다.
- 목록과 상세 패널은 독립 스크롤 구조를 사용한다.

## 2. 공통 화면 규칙

- 값이 없는 필드는 `-`로 표시한다.
- 배열 값이 비어 있으면 해당 영역을 숨기거나 빈 상태 문구를 표시한다.
- 날짜는 `YYYY.MM.DD` 또는 서비스 표준 포맷으로 표시한다.
- 금액은 내부 데이터에서 원 단위로 관리하되 화면에서는 `N만원/시간` 형식으로 변환한다.
- 전임강사는 fee와 별개로 `전임강사` 배지를 표시한다.
- 전임강사의 fee는 화면에서 직접 노출하지 않는다.
- fallback 상태에서는 상단에 `임시 데이터 표시 중` 배너를 표시한다.

## 3. 공통 상태 정의

- `idle`: 초기 상태
- `loading`: 데이터 로딩 중
- `success`: 정상 렌더링
- `empty`: 결과 없음
- `partial`: 일부 필드 누락
- `error`: API 또는 처리 실패
- `fallback`: fallback 데이터 사용 중

### Feature A. 강사 목록 조회

#### 목적
- 사용자가 대시보드에 들어오자마자 강사 후보를 빠르게 훑어볼 수 있어야 한다.

#### 화면 구조
- 좌측 목록 영역 상단에는 제목, 전체 강사 수, 마지막 업데이트 시각, 검색창, 카테고리 필터, 정렬 선택을 배치한다.
- 목록 아이템은 카드형 리스트로 구성한다.

#### 목록 아이템 구성
- 좌측: 순위 배지
- 중앙: 이름, 대표 카테고리, 소속, 전문분야
- 우측: 점수, 총 출강 횟수

#### 표시 규칙
- 전문분야는 최대 2개만 표시한다.
- 점수는 API 응답값을 기준으로 소수점 한 자리까지 반올림해 표시한다.
- 점수가 없으면 순위만 표시한다.
- 총 출강 횟수는 `N회` 형식으로 표시한다.
- 전임강사인 경우 이름 옆 또는 메타 정보 영역에 `전임강사` 배지를 표시한다.
- `categories`가 있으면 첫 번째 값을 대표 카테고리로 표시한다.
- `categories`가 비어 있거나 소속이 없으면 `-`로 표시한다.

#### 동작 방식
- 목록은 기본적으로 점수 높은 순으로 정렬한다.
- 강사를 클릭하면 상세 패널이 열린다.
- 현재 선택된 강사는 배경색 또는 테두리로 구분한다.

#### 완료 기준
- 목록이 정상 렌더링된다.
- 선택 상태가 명확히 보인다.
- 일부 값이 비어 있어도 화면이 깨지지 않는다.

### Feature B. 검색

#### 목적
- 사용자가 원하는 강사를 텍스트로 빠르게 찾을 수 있어야 한다.

#### 검색 대상
- 강사명
- 카테고리 배열
- 전문분야
- 소속

#### 동작 방식
- 검색창 입력과 동시에 결과를 갱신한다.
- 검색 버튼은 두지 않는다.
- 검색어가 비어 있으면 전체 목록으로 돌아간다.

#### 규칙
- 앞뒤 공백 제거
- 대소문자 구분 없음
- 부분 일치 검색
- 초성 검색, 형태소 검색, 오타 교정은 지원하지 않음

#### 완료 기준
- 강사명, 카테고리, 전문분야, 소속으로 검색할 수 있다.
- 결과가 없으면 `검색 결과가 없습니다`를 표시한다.

### Feature C. 필터

#### 목적
- 사용자가 카테고리 기준으로 목록을 빠르게 좁혀볼 수 있어야 한다.

#### 화면 위치
- 검색창 아래, 정렬 선택과 같은 상단 제어 영역에 배치한다.

#### 동작 방식
- 단일 선택 카테고리 필터를 사용한다.
- 기본값은 `전체`다.
- 필터 변경 시 목록 결과를 즉시 갱신한다.

#### 규칙
- 검색과 함께 동시에 적용된다.
- 정렬 상태는 유지한다.
- 카테고리 필터는 `categories` 배열에 선택한 값이 포함된 강사를 노출한다.
- 선택된 강사가 필터 결과에 남아 있으면 선택을 유지한다.
- 선택된 강사가 결과에서 제외되면 선택 상태를 해제하고 상세 패널을 빈 상태로 전환한다.

#### 완료 기준
- `전체` 선택 시 전체 목록으로 돌아간다.
- 필터 결과가 없으면 빈 상태 문구를 표시한다.

### Feature D. 정렬

#### 목적
- 사용자가 원하는 기준으로 목록 순서를 바꿀 수 있어야 한다.

#### 정렬 옵션
- 점수순
- 순위순
- 출강순
- 최근 활동순
- 단가순
- 이름순

#### 동작 방식
- 검색과 필터 결과에 정렬을 적용한다.
- 정렬 변경 시 목록 순서를 즉시 갱신한다.

#### 규칙
- 기본 정렬은 점수순이다.
- tie-breaker는 순위 오름차순, 이름 오름차순이다.
- 비교 가능한 값이 없는 경우 목록 하단으로 보낸다.

#### 완료 기준
- 모든 정렬 옵션이 정상 동작한다.

### Feature E. 강사 상세 조회

#### 목적
- 선택한 강사의 상세 정보를 같은 화면 안에서 바로 확인할 수 있어야 한다.

#### 화면 구조
- 상세 패널은 우측 고정 패널로 제공한다.
- 패널 상단에는 이름, 메타 정보, 프로필 요약을 배치한다.
- 그 아래에 핵심 수치, 점수/만족도, 운영 인텔리전스, 이력, 메모 순으로 배치한다.

#### 필수 표시 정보
- 이름
- 소속
- 연락처
- 카테고리 배열
- 전문분야
- 강사 프로필 요약
- 총 출강 횟수
- 최근 6개월 활동
- 기본 단가 또는 단가 상태
- 강의 이력 요약

#### 표시 규칙
- `profile_summary` 값이 있으면 이름 및 메타 정보 아래, 핵심 수치 위에 표시한다.
- `profile_summary`가 없으면 영역을 숨긴다.
- 전임강사는 상세 상단에서 `전임강사` 배지를 표시한다.
- 전임강사의 fee는 화면에서 직접 노출하지 않는다.
- 상세 패널에서는 `categories` 전체를 표시할 수 있다.
- 필수 정보 일부 누락 시 `일부 데이터 누락` 배지를 표시한다.

#### 상태 처리
- 로딩 중에는 상세 패널 로딩 UI를 표시한다.
- 잘못된 ID 또는 조회 실패 시 `강사 정보를 찾을 수 없습니다` 또는 오류 상태를 표시한다.
- fallback 데이터가 있으면 fallback 상세를 표시한다.

#### 완료 기준
- 강사 클릭 시 상세 패널이 열린다.
- 일부 필드 누락 시에도 화면이 깨지지 않는다.

### Feature F. 핵심 수치 표시

#### 목적
- 상세 화면 상단에서 강사의 활동 규모와 단가 상태를 빠르게 파악할 수 있어야 한다.

#### 표시 항목
- 총 출강 횟수
- 최근 6개월 출강 횟수
- 대표 출강 단가
- 단가 변동

#### 규칙
- 4개 카드형 블록으로 한 줄 배치한다.
- 대표 출강 단가는 `teaching_history.deal_fee_hourly` 유효값의 최빈값으로 계산한다.
- 단가 변동은 `fee_history` 기준으로 계산한다.
- 기록이 없으면 `변동 없음`으로 표시한다.
- 값이 없으면 `-`로 표시한다.

#### 완료 기준
- 상세 패널 상단에 4개 지표가 정상적으로 보인다.

### Feature G. 점수 구성 요소 및 만족도 표시

#### 목적
- 종합 점수와 점수 구성 요소, 만족도를 함께 확인할 수 있어야 한다.

#### 표시 항목
- 종합 점수
- 점수 구성 요소 7개
- 만족도 평균
- 만족도 건수
- 만족도 대체 여부

#### 규칙
- 종합 점수와 `score_breakdown` 각 항목은 소수점 한 자리까지 반올림해 표시한다.
- 점수 구성 요소는 항목별 리스트 또는 시각적으로 구분된 블록으로 표시한다.
- 점수 구성 요소 라벨은 `courses`, `satisfaction`, `slack`, `recency`, `salesmap`, `email`, `ops_channel` 키와 1:1 대응해야 한다.
- 만족도는 0~5 범위로 표시한다.
- 중앙값 대체가 적용된 경우 `대체값 사용` 또는 동등한 상태를 표시할 수 있다.

#### 완료 기준
- 종합 점수와 score_breakdown이 있으면 함께 표시된다.
- 만족도 데이터가 있으면 함께 표시된다.

### Feature H. 운영 인텔리전스 표시

#### 목적
- 추천/지양/리스크/운영 확인 필요 사항을 구조화해 보여줘야 한다.

#### 표시 항목
- 추천 대상
- 지양 대상
- 리스크 정보
- 운영 확인 필요 사항

#### 규칙
- 추천 대상과 지양 대상은 태그 또는 배지 형태로 표시한다.
- 리스크 정보는 일반 정보와 구분되는 강조 표현을 사용한다.
- 운영 확인 필요 사항은 별도 카드 또는 강조 영역으로 표시한다.
- 데이터는 노션 외 다른 소스도 허용한다.
- 화면은 저장된 운영 인텔리전스 결과만 표시한다.
- 상세 조회 시점에 운영 인텔리전스를 실시간 생성하지 않는다.

#### 완료 기준
- 값이 있는 항목만 선택적으로 노출된다.

### Feature I. 강의 이력 표시

#### 목적
- 강사의 실제 출강 이력을 최신순 표 형태로 제공해야 한다.

#### 표시 항목
- 기업명
- 과정명
- 일정
- 출강 단가
- 특이사항

#### 규칙
- 최신순 정렬
- 유효하지 않은 행 제외
- 최근 30건까지만 노출
- 30건 초과 시 `N건 더 있음` 표시
- 강사료 없으면 `-`
- 특이사항 없으면 빈칸 또는 `-`

#### 완료 기준
- 이력이 있으면 표로 노출된다.
- 이력이 없으면 `강의 이력이 없습니다`를 표시한다.

### Feature J. 단가 이력 표시

#### 목적
- 강사의 단가 또는 강사료 변동 흐름을 보여줘야 한다.

#### 표시 항목
- 날짜
- 금액
- 변경 사유 또는 컨텍스트
- 출처

#### 규칙
- 최신순 정렬
- 타임라인형 블록으로 표시
- 변경 사유가 없으면 `-`
- 특수 금액은 일반 시간당 단가와 혼동되지 않도록 별도 맥락으로 표시한다.
- 특수 금액 항목에는 `특수 금액`, `건당`, `출장비 별도` 등 구분 가능한 라벨 또는 설명을 함께 표시한다.
- 복수 단가 표기나 시간당 단가로 확정되지 않은 값은 기본 단가처럼 강조하지 않는다.

#### 완료 기준
- fee_history가 있을 때 섹션이 노출된다.
- 이력이 없으면 숨기거나 `이력 없음`을 표시한다.

### Feature K. 운영 메모 표시

#### 목적
- 운영 판단에 필요한 원문 메모를 보여줘야 한다.

#### 규칙
- 메모는 원문 기반으로 표시한다.
- 내부 사용자 전용 서비스이므로 이번 버전에서는 마스킹하지 않는다.
- 메모가 없으면 섹션을 숨긴다.

#### 완료 기준
- 메모가 있으면 상세 하단에 표시된다.

### Feature L. 데이터 상태 및 새로고침

#### 목적
- 데이터 최신 상태와 갱신 가능 여부를 보여줘야 한다.

#### 표시 항목
- 마지막 업데이트 시각
- 소스별 연결 상태
- 소스별 최근 수집 시각
- 새로고침 버튼

#### 동작 방식
- 새로고침 버튼 클릭 시 각 소스의 업데이트 여부를 다시 조회한다.
- 변경 데이터가 있으면 반영한다.
- 새로고침 중에는 버튼을 비활성화한다.
- 실패 시 기존 데이터를 유지한다.

#### 완료 기준
- 새로고침 클릭 시 로딩 상태가 보인다.
- 성공 시 최신 시각이 갱신된다.

### Feature M. fallback 처리

#### 목적
- 최신 데이터 조회 실패 시에도 서비스 사용 가능 상태를 유지해야 한다.

#### 규칙
- 순서: 최신 데이터 -> 마지막 정상 데이터 -> 정적 baseline
- fallback 사용 시 상단 배너 표시
- fallback 상태에서도 목록, 검색, 필터, 정렬, 상세 조회가 가능해야 한다.

#### 완료 기준
- API 실패 시 화면이 깨지지 않는다.
- fallback 여부가 사용자에게 보인다.

### Feature N. 마스터 데이터 조회 구조

#### 목적
- 프론트엔드는 병합 완료된 단일 마스터 레코드 기준으로 화면을 구성해야 한다.

#### 규칙
- 프론트는 원본 소스 구조를 직접 다루지 않는다.
- 목록과 상세는 모두 마스터 레코드를 기준으로 렌더링한다.
- 일부 소스가 실패해도 마스터 레코드가 있으면 조회 가능해야 한다.

#### 완료 기준
- 화면 구현이 원본 소스 구조에 직접 의존하지 않는다.

### Feature O. 만족도 작성

#### 목적
- 내부 사용자가 강사 만족도 기록을 직접 작성할 수 있어야 한다.

#### 화면 위치
- 상세 패널 내 만족도 표시 영역 또는 그 인접 영역에 작성 UI를 배치한다.

#### 입력 항목
- 만족도 점수
- 코멘트
- 기업명
- 과정명
- 응답일

#### 동작 방식
- 사용자가 점수와 선택 입력값을 작성해 저장할 수 있어야 한다.
- 저장 성공 시 `POST /api/instructors/{id}/satisfaction` 응답의 `updated_satisfaction`를 현재 상세 패널에 즉시 반영한다.
- 저장 성공 직후 `GET /api/instructors/{id}`를 다시 호출해 서버 계산 기준의 `satisfaction`, `score`, `score_breakdown`을 동기화한다.
- 저장 실패 시 오류 메시지를 표시한다.

#### 규칙
- 점수는 0~5 범위만 허용한다.
- 코멘트는 선택 입력이다.
- 작성된 만족도는 `satisfaction_records`에 저장되고 집계값에 반영된다.
- 프론트는 만족도 평균, 건수, 점수 총합을 클라이언트에서 낙관적으로 재계산하지 않는다.

#### 완료 기준
- 사용자가 만족도 기록을 저장할 수 있다.
- 저장 후 상세 화면의 만족도 값이 갱신된다.

## 5. 데이터 검증 규칙

- 이 섹션의 `rule_code`는 `validation_issues.rule_code`와 파이프라인 검증에 공통으로 사용한다.

### 5-1. 수치 검증

- 강사료는 0 이상이어야 한다.
- 일반 강사의 강사료는 50,000원~500,000원 범위를 벗어나면 경고를 표시한다. 전임강사는 이 범위 검증에서 제외한다.
- `base_fee_hourly`와 최빈 출강 단가 차이가 2배 이상이면 경고를 표시한다.
- 만족도는 0~5 범위 안에 있어야 한다.
- `total_courses`와 `recent_courses_6mo`는 음수가 될 수 없다.

### 5-2. 연락처 검증

- 전화번호와 이메일은 기본 형식 검증을 수행해야 한다.
- 형식이 올바르지 않은 경우 원문을 그대로 신뢰하지 않고, 검토 대상 또는 빈값 처리할 수 있어야 한다.

### 5-3. 단가 및 이력 검증

- 강사료 변동이 3배 이상이거나 특수비용이 포함된 경우 자동 수정으로 제거한다.
- 비정상적으로 보이는 단가 변동은 자동 제외하지 않고 우선 검토 대상으로 표시한다.
- 강사료 이력과 강의 이력 간에 명백한 충돌이 있는 경우 검토 대상으로 남길 수 있어야 한다.
- 전임강사, 특수 계약 건, 내부 정산 기준이 적용된 데이터는 일반 강사와 동일한 규칙으로 단정하지 않는다.
- 콘텐츠 제작비, 건당 금액, 출장비 포함 금액 등은 일반 시간당 강사료와 분리해서 해석해야 한다.
- 특수 금액은 `base_fee_hourly` 계산에 직접 사용하지 않는다.
- 강사료 변동 이력은 시간순으로 자동 정렬한다.
- `fee_history`의 현재 금액과 `base_fee_hourly`가 불일치하면 자동 수정한다.

### 5-4. 이력 정합성 검증

- `total_courses`는 `teaching_history`의 유효 행 수 기준으로 재계산한다.
- `recent_courses_6mo`는 `teaching_history`의 날짜 기준으로 재계산한다.
- `teaching_history`에서 company + course + dates 키가 동일한 중복 행은 자동 제거한다.
- 계약시트 원본 행 수와 `teaching_history(source=contract_sheet)` 수가 불일치하면 경고를 표시한다.
- 날짜 형식은 `YYYY-MM-DD`로 자동 정규화한다.

### 5-5. 문자열 정제

- 기업명과 과정명에 포함된 불필요한 접두사, 노이즈, 중복 텍스트는 자동 제거한다.
- 비고에서 행정정보는 자동 제거한다.
- 운영 메모에서 계약정보는 자동 제거한다.

### 5-6. 운영 예외 보존

- 전임강사, 실습코치, 특수 계약 여부와 같은 운영상 중요한 플래그는 정제 과정에서 제거하지 않고 유지해야 한다.
- 실습코치 flag와 `score = 0`의 정합성을 검증하고, 불일치 시 자동 수정한다.
- 자동발견된 강사의 `categories` 또는 `specialties`가 빈칸이면 경고를 표시한다.
- 이력 50건 이상인데 `score < 30`이면 역전 경고를 표시한다.

### 5-7. 검증 결과 처리

- 검증 실패 항목이 있더라도 전체 화면이 깨지지 않아야 한다.
- 경미한 문제는 빈값 또는 경고 상태로 처리할 수 있어야 한다.
- 중요한 충돌이나 의심 데이터는 운영 검토 대상으로 남길 수 있어야 한다.
- 자동 수정이 적용된 항목은 수정 내역을 기록한다.

### 5-8. 검증 규칙 요약

## 6. 공통 완료 기준

- 목록, 상세, 점수, 운영 인텔리전스, 이력, 새로고침, fallback이 모두 한 서비스 안에서 연결되어 동작한다.
- 검색, 필터, 정렬, 상세 선택 상태가 서로 충돌 없이 유지된다.
- 일부 데이터가 누락되거나 일부 소스가 실패해도 전체 화면이 깨지지 않는다.
- fallback 사용 여부와 데이터 상태를 사용자가 구분할 수 있다.
