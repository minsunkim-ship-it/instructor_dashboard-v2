## 1. 서비스 범위
- 서비스 성격: 내부 운영 대시보드
- 주요 목적: 데이원 B2B 구성원이 강사 정보를 한 화면에서 탐색, 조회, 비교 판단할 수 있게 한다.
- 이번 버전 성격: 조회 중심 서비스이되, 만족도 작성 기능은 포함한다.
- 이번 버전 제외: 강사 비교 전용 화면, 자동 배정, 계약/정산/메시지 발송, 모바일 앱, JSON import/export, 고도화된 자동 인텔리전스 생성

## 2. 인증 및 접근 정책
- 로그인 방식: Google 로그인
- 접근 허용 계정: `@day1company.co.kr`
- 도메인 외 계정: 접근 불가
- 이번 버전에서는 로그인한 사용자 모두 동일 권한을 가진다.

## 3. 기본 화면 구조
- 기본 레이아웃: `목록 + 상세 패널`
- 첫 진입 상태: 상세 패널은 빈 상태
- 상세 표시 방식: 목록에서 강사를 선택한 뒤에만 상세 정보 표시
- 플랫폼 기준: 데스크톱 우선

## 3-1. 프로필 필드 정규화 정책
- 카테고리는 단일 문자열이 아니라 `categories` 배열로 저장한다.
- 노션 multi_select 카테고리는 순서를 유지한 배열 그대로 저장한다.
- 목록 화면에서는 `categories`의 첫 번째 값을 대표 카테고리로 표시한다.
- 카테고리 필터는 단일 선택을 유지하되, 선택 값이 `categories` 배열에 포함된 강사를 노출한다.
- multi_select 형태의 소속정보는 순서를 유지한 채 `, `로 join하여 `affiliation`에 저장한다.

## 4. 강사 동일인 판정 정책
- 1차 식별자: `instructor_id`
- 2차 식별 기준: 강사명
- 이름 비교 방식: exact match만 사용
- alias 정책: 사용하지 않음
- 보조 검증값: 전화번호, 이메일, `course_id`, 소속
- 이름이 같더라도 연락처가 다르면 자동 병합하지 않는다.
- 이름이 같고 연락처가 없으면 운영 검토 대상으로 남긴다.

## 5. 동명이인 처리 정책
- 동명이인은 이름 끝 식별 문자로 구분한다.
- 표기 예시: `홍길동`, `홍길동B`
- suffix가 다르면 서로 다른 강사로 간주한다.
- suffix는 병합 시 제거하지 않는다.

## 6. 전임강사 판정 정책
- 전임강사 여부는 별도 JSON 리스트를 기준으로 판단한다.
- 전임강사 여부와 fee는 서로 다른 속성으로 관리한다.
- 전임강사는 목록과 상세에서 `전임강사` 상태값으로 별도 표시한다.

## 7. 전임강사 fee 정책
- 전임강사 fee는 노션에 기재된 기본 강사료 또는 fee_note를 기준으로 사용한다.
- 노션에 시간당 강사료가 명확히 있으면 해당 값을 `base_fee_hourly`로 사용한다.
- 노션에 시간당 강사료가 명확하지 않으면 `base_fee_hourly`는 내부 데이터에서만 관리하고 화면에는 노출하지 않는다.
- 전임강사라고 해서 자동으로 `0원` 처리하지 않는다.
- 화면에서는 전임강사 fee 자체를 보여주지 않고 `전임강사` 상태만 표시한다.

## 8. 특수 금액 처리 정책
- 콘텐츠 제작비, 건당 금액, 출장비 포함 금액, 개발비 등은 일반 시간당 강사료와 분리해서 해석한다.
- 특수 금액은 `base_fee_hourly` 계산에 직접 사용하지 않는다.
- 특수 금액은 fee_note 또는 별도 설명 필드로 관리한다.
- 단가 이력과 기본 단가를 혼동하지 않도록 분리 저장한다.
- 아래 키워드가 포함된 금액 정보는 특수 금액 후보로 본다.
  - `콘텐츠`, `제작`, `개발비`, `출장비`, `별도`, `건당`, `프로젝트`, `패키지`, `특강`, `자료개발`, `원고`, `감수`
- 시간당 단가로 명확히 해석되지 않는 표현은 특수 금액으로 분류한다.
  - 예: `300만원/건`, `출장비 별도`, `기본 25만 / 심화 35만 / 특강 55만`
- 동일 강사의 일반 출강료 분포 대비 3배 이상 큰 금액은 기본 단가 후보에서 제외하고 특수 금액 후보로 본다.
- 기본 단가 후보로 인정하려면 아래 조건을 모두 만족해야 한다.
  - 시간당 단가로 명확히 해석 가능하다.
  - 특수 금액 키워드가 포함되어 있지 않다.
  - 동일 강사의 다른 일반 출강료와 비교했을 때 과도한 이상치가 아니다.
  - 노션 기본 강사료 또는 fee_note, 세일즈맵, 계약시트 중 하나에서 확인 가능하다.
- 키워드 판정의 적용 범위:
  - 키워드 기반 특수 금액 판정은 **금액 자체를 직접 기술하는 텍스트 필드**에서만 적용한다.
  - 적용: Notion `fee_note` (기본 강사료를 직접 기술).
  - 미적용: `teaching_histories.fee_extra` (강사료 외 별도 항목), `teaching_histories.special_notes` (계약 특이사항) — 이들은 기본 hourly row를 직접 기술하지 않는다.
  - 미적용 필드의 키워드는 별도 special evidence/이력으로 취급하되, 동일 row의 `deal_fee_hourly`를 자동으로 특수 금액으로 전환하지 않는다.
- 기본 hourly row의 `is_special_amount` 판정:
  - 해당 row의 금액 자체 표현(예: Notion `fee_note`)에 키워드가 있거나, 동일 강사 일반 출강료 분포 대비 3배 이상 이상치면 `TRUE`.
  - 그 외 필드의 키워드만으로는 자동 특수 전환하지 않는다.

## 9. Engagement Score 정책
- 총점: 100점
- 점수 계산 시점: 현재 병합된 강사 데이터를 기준으로 계산
- 점수 구성 요소:
  - 출강횟수 35
  - 만족도 15
  - 슬랙 활동 15
  - 최근성 15
  - 세일즈맵 딜 10
  - 이메일 활동 5
  - 운영 채널 활동 5
- 정규화 방식: 전체 강사 중 최대값 대비 비율
- 만족도 결측치 처리: 전체 수집 강사의 중앙값으로 대체
- 최근성 계산: 슬랙, 세일즈맵, 지메일 중 가장 최근 활동일 기준 지수 감쇠
- 실습코치로 분류된 강사는 Engagement Score 0점 처리

## 10. 실습코치 판정 정책
- 실습코치 판정은 기존 기준을 유지한다.
- 실습코치 판정은 아래 3-Layer 기준을 순서대로 적용한다.
- L1 후보 판정:
  - 계약시트에서 해당 강사의 계약 유형 또는 상세 유형 중 `보조강사`, `코치`, `실습코치`, `멘토`, `문항개발` 비율이 정규강사 비율보다 높으면 실습코치 후보로 분류한다.
- L2 정규강사 보호:
  - `base_fee_hourly >= 100000` 이고 `categories`와 `specialties`가 모두 비어 있지 않으면 실습코치 후보에서 제외한다.
- L3 전임강사 보호:
  - 전임강사 리스트에 포함된 강사는 실습코치 후보에서 무조건 제외한다.
- 최종 판정:
  - 위 보호 규칙을 통과한 후보만 실습코치로 분류한다.

## 11. 추천/지양 및 운영 인텔리전스 정책
- 추천 대상, 지양 대상, 리스크, 운영 확인 필요 사항은 노션 외 다른 소스도 허용한다.
- 구조화된 필드가 소스에 직접 존재하면 해당 값을 우선 사용한다.
- 구조화된 필드가 없고 원문 근거만 있는 경우, LLM을 이용해 추천 대상, 지양 대상, 리스크, 운영 확인 필요 사항으로 구조화할 수 있다.
- LLM은 원문 근거 기반 정리만 수행하며, 근거 없는 추측이나 새로운 사실 생성은 허용하지 않는다.
- 근거가 부족하면 해당 필드는 비워 둔다.
- 운영 인텔리전스 구조화 결과는 파이프라인 단계에서 생성하고 DB에 저장한다.
- 화면 조회 시마다 운영 인텔리전스를 다시 생성하지 않는다.
- 운영 인텔리전스는 구조화된 정보로 표시한다.
- 운영 메모와 운영 인텔리전스는 서로 다른 영역으로 분리한다.

## 12. 만족도 정책
- 만족도는 상세 화면에서 표시한다.
- 만족도는 Engagement Score 계산에도 사용한다.
- 만족도 값은 0~5 범위로 관리한다.
- 이번 버전에서는 만족도 조회와 작성 기능을 모두 포함한다.

## 13. 데이터 소스 우선순위 정책
- 기본 우선순위: `계약시트 > 노션 > 세일즈맵 > 지메일/슬랙`
- 강사 기본 프로필: 노션 우선
- 출강 이력: 계약시트 우선
- 회사/과정명 보강: 세일즈맵 보조 사용
- 추천/지양/리스크/운영 확인 필요 사항: 복수 소스 허용
- 충돌 시 상위 우선순위 소스를 신뢰한다.

## 14. fallback 정책
- fallback 정책은 기존 기준을 유지한다.
- 최신 데이터 조회에 실패하면 마지막 정상 저장 데이터를 사용한다.
- 마지막 정상 저장 데이터도 없으면 정적 baseline 데이터를 사용한다.
- fallback 사용 여부는 사용자에게 표시한다.

## 15. refresh 정책
- 수동 새로고침 기능은 제공한다.
- 새로고침은 데이터 업데이트가 있는지 다시 조회하고, 변경된 데이터가 있으면 반영한다.
- 새로고침 실패 시 기존 데이터는 유지한다.

## 16. 민감정보 노출 정책
- 이번 버전은 내부 사용자 전용 서비스이므로 연락처와 운영 메모는 마스킹 없이 노출한다.
- 명시적 민감정보 마스킹 정책은 이번 버전에서 적용하지 않는다.

## 17. 마스터 데이터 저장 정책
- 마스터 데이터 저장소는 Railway DB를 사용한다.
- 최신 데이터, 마지막 정상 데이터, 운영 기준 데이터는 DB를 기준으로 관리한다.

## 18. 상태 처리 정책
- 공통 상태: `idle`, `loading`, `success`, `empty`, `partial`, `error`, `fallback`
- 필수 정보 일부 누락 시 `partial`
- API 또는 처리 실패 시 `error`
- fallback 데이터 사용 시 `fallback`
- 각 상태는 화면에서 사용자에게 구분 가능해야 한다.

## 19. 현재 미정 사항
