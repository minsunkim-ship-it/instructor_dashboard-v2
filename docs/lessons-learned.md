# Lessons Learned

## Role
이 문서는 이번 프로젝트에서 실제로 놓쳤던 것을 남기고, 다음 프로젝트에서는 같은 문제를 반복하지 않기 위한 기본 규칙을 정하는 회고 문서다.

## Scope
- 남길 것:
  - 문서-구현 불일치
  - 배포/env 누락
  - 외부 source hang
  - 데이터 품질 오판정
  - 완료 판정 기준이 흐렸던 것
- 남기지 않을 것:
  - 단순 구현 디테일
  - 일회성 코드 버그
  - 이미 다시 안 쓸 세부 상황

## 1. 문서-구현 불일치를 너무 늦게 발견했다

### 실제로 놓친 것
- 문서에는 인증, 권한, 핵심 API/화면 책임이 있었지만 구현 반영과 확인이 늦었다.
- 화면에서 보여주는 기준과 내부 집계 기준이 문서로 먼저 고정되지 않아, 목록과 상세가 다른 숫자를 보여줬다.
- 문서에 없는 노출/집계 규칙을 구현 중에 즉석으로 결정하는 일이 생겼다.
- 같은 성격의 source인데도 인증 방식과 접근 계약이 collector마다 달라졌다.
  - 예: 계약시트는 service account, 다른 시트 source는 user OAuth를 사용해 문서와 실제 운영 경로가 벌어졌다.

### 왜 못 잡았나
- 문서 기준 필수 흐름을 시작 전에 P0 게이트로 따로 분리하지 않았다.
- 구현 단위 확인은 했지만, 문서와 실제 동작을 한 번에 대조하는 검사를 늦게 했다.
- 문서가 없거나 애매한 부분을 바로 gap으로 기록하지 않고 구현으로 메웠다.

### 다음 기본 규칙
- 구현 시작 전에 필수 사용자 흐름 3~5개를 먼저 적는다.
- 인증, 권한, 핵심 API, 핵심 화면 책임은 문서 기준으로 먼저 고정한다.
- 화면 노출 기준과 집계 기준은 구현 전에 문서로 먼저 정한다.
- 문서에 있고 코드에 없으면 “나중에 붙일 예정”이 아니라 gap으로 즉시 기록한다.
- 같은 provider를 쓰는 source 묶음은 인증 전략을 한 문장으로 먼저 고정한다.
  - 예: “모든 Google Sheets source는 user OAuth refresh token으로 읽는다.”

## 2. 배포/env 문제를 너무 늦게 확인했다

### 실제로 놓친 것
- 배포가 떠 있는 것과 서비스가 정상 동작하는 것을 같은 의미로 취급했다.
- env나 런타임 설정이 맞지 않아도 메인 페이지가 뜨면 일단 성공처럼 해석하기 쉬웠다.
- 로컬에서 되는 것과 배포에서 되는 것을 분리해서 보지 못했다.
- `.env.example`에 있는 값과 실제 코드가 읽는 값이 벌어지는 구간이 있었다.
  - 예: 설정 템플릿에는 남아 있지만 실제 런타임은 더 이상 사용하지 않는 변수, 반대로 실제로 필요한 변수인데 운영 문서에 덜 반영된 경우.
- 같은 source 이름으로 불렀지만, 실제로는 다른 env 해석 경로나 다른 외부 scope를 보고 있는 run을 한동안 같은 것으로 오해했다.
  - 예: Notion은 `sourceSyncLog`에 한때 `fetchedCount=300`으로 남아 있었고, 현재 collector는 같은 시점 아닌 live source에서 `776`을 읽었다. 응답이 덜 온 문제가 아니라, 그 시점 run이 다른 source scope / 다른 resolved env surface를 보고 있었을 가능성을 먼저 봐야 했다.

### 왜 못 잡았나
- 배포 직후 실데이터 API까지 확인하는 절차가 없었다.
- 필수 env와 외부 연동 자격증명, 외부 경로 의존성을 나눠서 보지 않았다.
- 재배포/재시작 후 실제 반영 여부를 체크리스트로 강제하지 않았다.
- sourceSyncLog에 “무슨 source를 봤는지”를 남기지 않아, 같은 sourceType이라도 실제 external scope가 달랐는지 바로 구분할 수 없었다.

### 다음 기본 규칙
- 배포 직후 `메인 URL`, `헬스 체크 API`, `실데이터 API`를 반드시 확인한다.
- 로컬 성공과 배포 성공을 같은 말로 쓰지 않는다.
- 필수 env는 목록으로 관리하고, 저장 후 실제 런타임에서 다시 확인한다.
- 외부 연동은 env 누락, 권한 누락, 경로 누락을 나눠서 본다.
- `.env.example`, 문서, 런타임 코드가 같은 env surface를 쓰는지 같이 검증한다.
- 더 이상 안 쓰는 env는 템플릿과 문서에서 바로 제거한다.
- 외부 source sync 로그에는 최소한 아래를 남긴다.
  - resolved external identifier
  - fetched pages
  - fetched raw count
- “응답이 정상 종료됐다”와 “같은 source를 보고 있었다”를 같은 의미로 취급하지 않는다.

## 3. 외부 source hang과 runtime 종료 보장을 기능보다 늦게 봤다

### 실제로 놓친 것
- 외부 source 하나가 전체 refresh를 오래 붙잡거나 `running` 상태를 남기는 상황을 늦게 봤다.
- source별 실패나 지연이 전체 orchestration 해석을 흐리게 만들었다.
- source가 기술적으로 끝난 것과 실제로 usable 상태인지가 분리돼 있지 않았다.
- route가 실제로 어느 단계에서 멈추는지 보이지 않아, 수집 문제인지 저장 문제인지 한동안 잘못 추정했다.

### 왜 못 잡았나
- source별 timeout, budget, concurrency를 기본값으로 넣지 않았다.
- route를 먼저 붙이고 collector 종료 보장과 단독 benchmark를 나중에 봤다.
- 외부 source 권한/접근 문제를 실제 자격증명으로 빨리 확인하지 않았다.

### 다음 기본 규칙
- 모든 외부 source collector에 timeout, budget, concurrency limit을 넣는다.
- route 연결 전에 source 단독 benchmark와 종료 보장을 먼저 확인한다.
- `running` 상태 정리 방법까지 설계한다.
- 외부 source는 실제 계정/실제 자격증명으로 먼저 접근 권한을 검증한다.
- 장시간 route에는 stage-level progress를 기본으로 남긴다.
  - `pipeline_runs.summary.stage`
  - `source_sync_logs` 진행 상태
  - 최소한의 서버 로그
- “collector hang”과 “store hot path 병목”을 구분할 수 있는 progress surface를 먼저 만든다.

## 4. 데이터 품질 문제를 기능 완료와 분리해서 보지 못했다

### 실제로 놓친 것
- 응답이 나온다는 것과 데이터가 맞다는 것을 같은 의미로 썼다.
- source가 `success`여도 실제 매칭/반영이나 화면 품질은 실패한 경우가 있었다.
- raw 보존, 파생값, 화면 노출 규칙이 분리되지 않아 raw 문자열이나 빈 값이 화면에 그대로 나왔다.
- fallback 우선순위, grouping 기준, 연도 범위 기준이 늦게 정리돼 목록/상세/집계가 어긋났다.
- 같은 business row가 여러 worksheet 또는 source에 반복될 때, dedupe 기준이 약하면 숫자만 부풀고 UI는 그 중복을 가려 더 헷갈려질 수 있다는 점을 늦게 봤다.
- source가 실제로 소유하지 않는 필드까지 매번 덮어쓰면서 no-op update amplification이 생겼다.

### 왜 못 잡았나
- 정상 케이스, 경계 케이스, 반례를 먼저 문서화하지 않았다.
- raw 보존과 화면 표현을 분리해서 설계하지 않았다.
- fallback 우선순위와 grouping 규칙을 코드에서 뒤늦게 맞추려 했다.
- 운영자 관점의 “수집 성공”과 사용자 관점의 “데이터가 맞음”을 같은 검증으로 취급했다.

### 다음 기본 규칙
- 데이터 품질은 최소 `정상 케이스`, `경계 케이스`, `오분류 반례`로 따로 본다.
- raw는 보존만 하고, 파생값은 parser/normalizer에서 한 번만 계산한다.
- fallback 우선순위와 grouping 기준은 구현 전에 문서로 정한다.
- source별로 `수집 성공`, `매칭/반영 성공`, `사용자 화면 품질 통과`를 따로 본다.
- 빈 값, raw 문자열 노출, 잘못된 grouping/집계도 데이터 품질 검증에 포함한다.
- dedupe는 “원본 식별자 dedupe”와 “business row dedupe”를 분리해서 설계한다.
- source별 소유 필드를 먼저 정하고, 소유하지 않는 필드는 sparse row가 덮어쓰지 않게 한다.
- 리스트/상세/API/집계가 같은 dedupe 기준을 쓰는지 확인한다.

## 5. 완료 판정 기준이 흐려서 “성공”의 의미가 섞였다

### 실제로 놓친 것
- `build PASS`, `배포 성공`, `API 응답`, `외부 source 종료`, `데이터 품질 통과`가 같은 “완료”처럼 쓰였다.
- `success`와 `partial`, 기술적 성공과 운영 준비 완료의 경계가 흐렸다.
- 완료라고 말할 수 있는 기준보다 진행 상황 보고가 먼저 나가는 순간이 있었다.
- clean rerun에서 `updated=0`처럼 재실행 수렴성이 확인되기 전에도 제품 수준 완료처럼 느끼기 쉬웠다.

### 왜 못 잡았나
- 완료 판정을 한 단계로만 봤다.
- 구현 성공, runtime 성공, 데이터 품질 통과를 별도 라벨로 관리하지 않았다.
- 운영자가 바로 해석할 수 있는 상태 지표가 부족했다.

### 다음 기본 규칙
- 완료 판정은 최소 아래 4단계로 분리한다.
  - 구현 성공
  - 배포 성공
  - route/runtime 성공
  - 데이터 품질 통과
- `success`는 “예외 없음”이 아니라 “기술적 성공 + partial 조건 없음”으로 정의한다.
- 보고에는 현재 달성 단계와 남은 단계를 함께 적는다.
- 핵심 흐름, 헬스 체크, 데이터 품질 확인 전에는 완료라고 말하지 않는다.
- 장기 운영 route는 “한 번 성공”보다 “clean rerun 수렴”을 완료 조건에 포함한다.
